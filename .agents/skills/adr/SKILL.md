# ADR

当设计过程中重大架构决策逐渐明确时，记录重要的架构决策。

## 资格条件

仅当以下三个条件全部满足时，才创建 ADR：

1. **难以逆转** — 以后更改该决策具有有意义的成本
2. **脱离上下文会令人困惑** — 未来的读者很可能会合理地想知道为什么选择了这种方法
3. **是真实权衡的结果** — 存在真正的备选方案，并且基于特定原因选择了其中一个

如果任一条件不满足，则不要创建 ADR。

创建 ADR 前先排除行为合同、安全策略、协议和兼容要求（归 Spec），以及实现机制、模块职责与数据流（归 RFC）。

架构形态、集成模式或技术选择只有在能说明长期反悔成本、真实可行备选、选择理由与接受的代价时才可能符合条件。边界、所有权或职责划分本身不构成 ADR；必须证明改变它会造成有意义的迁移成本或锁定。

不要为本地实现细节、显而易见的决策或容易逆转的决策创建 ADR。

## 位置

先按项目工件约定确定决定的属主。若决定由变更记录持有，就更新该记录，不另建重复 ADR。项目没有约定时，才使用 `docs/adr/` 作为默认位置。多上下文仓库按项目指令和上下文映射选择目录。

使用顺序编号：

`0001-slug.md`，`0002-slug.md`，...

对于包含多个上下文的代码库，将特定于上下文的 ADR 放在该上下文中，系统级 ADR 放在 ADR 根目录。

按需创建 ADR 目录。

## 编号

按项目约定与上下文映射确定 ADR 目录，扫描其中最大编号并加一。多上下文仓库若不同目录重复编号，引用时带上下文或路径以消除歧义。

## 格式

ADR 要简短，但必须把准入理由写具体。使用以下结构；“反悔成本”和“权衡”不可省略：

```md
---
status: proposed
---

# {决策标题}

## 背景

{触发该选择的约束或问题。}

## 决定

{选择了什么；引用相关 Spec/RFC，不复制其中的合同或机制。}

## 反悔成本

{改变决定时需要迁移什么，或会付出什么长期成本。}

## 权衡

{真实可行的备选、选择理由，以及接受的代价。}
```

无法具体填写“反悔成本”或“权衡”时，不创建 ADR。纯机制说明、规范性行为和修订过程分别写入 RFC、Spec 与 Spec 修订记录。

新 ADR 默认使用 `status: proposed`；只有决定获得明确批准后才改为 `accepted`。决定撤回或被取代时，保留原编号为存根并标记 `deprecated` 或 `superseded by ADR-NNNN`。

仅在存在未被“反悔成本”或“权衡”涵盖的重要非显然后果时，添加“后果”一节。
