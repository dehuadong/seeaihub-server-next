# Spec

Spec 是产品合同内容，回答“做什么、哪些不做、怎样算完成”，不是独立文件。

有 RFC 文件时，把 Spec 写在其中并与技术设计分节；没有 RFC 文件的小改动，可以由 Proposal 或既有工作项直接承载。

## 内容

按工作需要写清：

- 产品目标以及本次覆盖的用户或调用方；
- 产品范围与重要非目标；
- 正常、边界和失败时的可观察行为；
- 兼容性、安全、费用或运营方面的产品约束；
- 可观察、可判定的验收条件；
- 会影响实现的未解决产品决定。

Spec 不写模块划分、数据库表、内部接口、实现步骤或纯技术备选方案；这些属于同一 RFC 文件的技术设计部分或实现阶段。

已有 PRD 可以提供背景，但 Spec 必须就地写清本次能力的范围与验收。技术事实改变产品边界时：

1. 在 Spec 中解决或升级产品决定；
2. 更新范围、非目标与验收条件；
3. 检查同一 RFC 文件的技术设计和关联 RFC；
4. 再按修订后的 Spec 收敛技术设计。

## 稳定条件

Spec 作为实施输入，需要满足：

- 范围与非目标明确；
- 验收条件可观察、可判定；
- 影响实现的产品决定已经解决；
- 技术探索没有留下会改变范围的重要未知问题；
- 技术设计不需要猜测产品行为。

Spec 稳定不等于 RFC 已接受，也不授予执行授权。
