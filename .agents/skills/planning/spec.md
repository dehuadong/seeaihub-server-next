# Spec

当产品行为、范围和验收条件需要独立于工作项与技术设计演进时，创建或更新 Spec。

Spec 是产品合同，回答“做什么、哪些不做、怎样算完成”；RFC 回答“技术上怎么做到”。一份 Spec 可以由一份或多份 RFC 承接。

## 位置与生命周期

遵循项目工件注册表的存放位置、既有格式、评审和批准约定。复用同一产品能力已有的 Spec；注册位置变化不自动迁移历史工件。

Spec 在获得项目要求的评审与批准前不是稳定的实施输入。不要另造与项目约定竞争的状态词。

项目没有格式时，可以使用以下最小头部与章节，并按实际内容删去不适用部分：

```markdown
主题: <产品能力>
当前修订: <修订标识>
状态: <项目约定的状态>

# <标题>

## 目标
## 产品范围
## 非目标
## 可观察行为
## 验收条件
## 约束与兼容性
## 未解决问题
## 技术设计
```

“技术设计”只引用承接本 Spec 的 RFC，不复制设计正文。

## 内容边界

按工作需要写清：

- 产品目标以及本次覆盖的用户或调用方；
- 包含范围与重要非目标；
- 调用方可以观察到的正常、边界和失败行为；
- 兼容性、安全、费用或运营方面的产品约束；
- 可观察、可判定的验收条件；
- 会影响实现的未解决产品决定。

不要写模块划分、数据库表、内部接口、实现步骤或纯技术备选方案。这些属于 RFC 或实现。

已有 PRD 可以提供用户问题、价值和产品方向，但 Spec 必须就地写清本次能力的范围与验收，不能要求实施者先读 PRD 才知道要实现什么。

## 与探索性 RFC 往返

可行性问题会影响产品合同的，可以先创建 RFC 探索草案。Spec 可以引用探索结论，但产品选择仍由 Spec 拥有，不能把 RFC 中的临时假设直接当成产品事实。

探索结论改变范围时：

1. 在 Spec 中解决或明确升级产品决定；
2. 更新范围、非目标和验收条件；
3. 检查同一 Spec 下其他 RFC 是否受影响；
4. 再让相关 RFC 按新的产品合同收敛。

## 定稿条件

Spec 可以作为 RFC 定稿和实施门禁的稳定输入，需要满足：

- 范围与非目标明确；
- 验收条件可观察、可判定；
- 影响实现的产品决定已经解决；
- 技术探索没有留下会改变范围的重要未知问题；
- RFC 不需要自行猜测产品行为。

Spec 定稿不等于 RFC 已接受，也不授予执行授权。
