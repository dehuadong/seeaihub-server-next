# Spec

当产品行为、范围和验收条件需要跨工作项持续生效、由独立属主维护时，创建或更新 Spec；本次工作独有的行为与验收由工作项拥有。

Spec 是可验收的行为合同，回答“系统必须做什么、哪些不做、怎样判定符合”。范围包括产品行为、标准、接口契约、协议、安全策略、兼容边界和运维不变量。经评审接受的 Spec 修订是实现与验收的直接依据；项目登记的设计属主回答“技术上如何满足它”。

## 位置与生命周期

遵循项目配置中的存放位置与 Spec 格式、评审和批准约定。复用项目指定的同一产品能力的 Spec。

Spec 在获得项目要求的评审与批准前不是稳定的实施输入。工作项记录评审与批准状态；Spec 标明当前有效修订。不要另造与项目约定竞争的状态词。

项目没有格式时，可以使用以下最小头部与章节，并按实际内容删去不适用部分：

```markdown
主题: <产品能力>
当前修订: <本文件修订标识>
生效修订: <已接受的修订标识；尚无则写“无”>
状态: <项目约定的状态>

# <标题>

## 目标
## 产品范围
## 非目标
## 可观察行为
## 验收条件
## 约束与兼容性
## 未解决问题
## 技术设计

## 修订记录
| 修订 | 章节 | 合同变化摘要 | 状态／生效版本 |
```

Spec 应按要求和行为写到实施者无需猜测、评审者可以逐项判定的程度，包括输入、输出、状态变化、时序、错误、例外、权限、安全和兼容语义。不要以“产品层面”作为省略规范细节的理由。“技术设计”引用本次 Planning 中承接本 Spec 的 Agent Note；其他适用设计输入按项目配置引用，不复制设计正文。

起草修改时更新 `当前修订`，保留原 `生效修订`；评审接受后才更新 `生效修订`。修订记录只列修订标识、受影响章节、合同变化摘要、状态与生效版本，不写讨论、批准过程、选择理由或被否方案；这些分别归工作项与项目登记的决定属主。当前修订未获接受时，技术设计定稿与实施仍引用已接受的历史修订。若项目已有版本控制格式，沿用既有格式。

## 内容边界

按工作需要把规范性行为写到可实现、可验收的细度：

若改变某项细节会改变验收结果、兼容性、安全性或运行保证，该细节归产品合同；多种实现都能满足同一结果的内部做法归技术设计属主。

- 产品目标以及本次覆盖的用户或调用方；
- 包含范围与重要非目标；
- 调用方可以观察到的正常、边界和失败行为；
- 兼容性、安全、费用或运营方面的产品约束；
- 可观察、可判定的验收条件；
- 标准、接口契约、协议、安全策略、兼容边界和运维不变量；
- 会影响实现的未解决产品决定。

不要写决定形成过程、选择理由或被否方案；也不要写模块划分、数据库表、内部接口、实现步骤或纯技术备选方案。长期技术设计与决定归 Agent Note，实施过程归工作项。

已有 PRD 可以提供用户问题、价值和产品方向，但 Spec 必须就地写清本次能力的范围与验收，不能要求实施者先读 PRD 才知道要实现什么。

## 与探索性设计往返

可行性问题会影响产品合同的，可以先在 proposed Note 中创建探索草案。Spec 可以引用探索结论，但产品选择仍由产品合同属主拥有，不能把设计中的临时假设直接当成产品事实。

探索结论改变范围时：

1. 在 Spec 中解决或明确升级产品决定；
2. 更新范围、非目标和验收条件；
3. 检查同一 Spec 下其他设计是否受影响；
4. 再让相关设计按新的产品合同收敛。

## 定稿条件

Spec 可以作为设计定稿和实施门禁的稳定输入，需要满足：

- 范围与非目标明确；
- 验收条件可观察、可判定；
- 影响实现的产品决定已经解决；
- 技术探索没有留下会改变范围的重要未知问题；
- 设计不需要自行猜测产品行为。

Spec 定稿不等于设计已接受，也不授予执行授权。
