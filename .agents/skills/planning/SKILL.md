# Planning

把当前对话与项目上下文整理成最少但足够的规划工件。Spec 是产品合同内容；RFC 文件同时承载 Spec 与技术设计，不另建独立 Spec 文件。

## 1. 确定工作项

按项目工件注册表定位本次 Proposal 或既有工作项。它负责本次目标、选定交付范围、工作状态、批准证据和规划工件链接。

复用合适的既有工作项；确实需要新的规划根节点时才创建 Proposal，并读取 [proposal.md](./proposal.md)。

小改动可以在工作项内直接写清 Spec 和必要技术决定。需要本地长期合同或独立技术设计的，创建 RFC 文件。

## 2. 收敛 Spec 与技术设计

读取 [spec.md](./spec.md) 与 [rfc.md](./rfc.md)。RFC 文件分开写清：

- **Spec**：做什么、哪些不做、调用方能观察到什么、怎样算完成；
- **技术设计**：怎么实现、重要取舍、兼容与迁移、验证切入点。

可行性、成本、性能、兼容性、安全或上游限制会改变产品范围时，先在 RFC 草案中区分产品事实、临时假设和待决定问题。草案可以往返修改，但不能作为实施依据。

复杂能力按 [rfc.md](./rfc.md#rfc-集合) 的 RFC 集合规则拆分，避免遗漏或重复属主。

使用项目既有领域语言、ADR 和架构约束。形成或改变持久领域知识或架构决定时，使用 `domain-modeling` 判断是否需要 ADR。

## 3. 决定权限

在已同意的 Spec、既有架构和项目约束内，自主解决普通技术选择。

涉及未解决的产品、业务、兼容性、成本、风险、架构方向或其他价值判断时，交由用户决定，除非用户已经明确委托决定权。

## 4. Plan Review

必要规划内容形成后，读取 [review.md](./review.md)。有 RFC 文件时评审其中的 Spec、技术设计及整个 RFC 集合；没有 RFC 文件时评审工作项内的 Spec 与技术决定。

Spec 与技术设计问题回到承载它们的 RFC 文件；没有 RFC 文件时回到工作项。工作状态与批准证据回到 Proposal 或工作项。解决实质问题后重新评审。

## 5. 完成与交接

Planning 完成需要同时满足：

- Spec 已经稳定；
- 有 RFC 时，RFC 或 RFC 集合的职责边界完整且没有重复属主；
- 重要技术决定与验证设计足以指导实施；
- 所需决定已解决；
- Plan Review 通过；有 RFC 时，RFC 已按项目约定接受或批准。

若用户只要求规划，交付规划结果与评审证据后结束。端到端任务继续进入项目的 Implementation Gate，并单独核对执行授权。
