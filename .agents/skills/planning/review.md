# Plan Review

确定被评审的 Proposal 或既有工作项、选定范围，以及适用的 RFC 或 RFC 集合。小改动没有 RFC 文件时，评审工作项内的 Spec 与技术决定。

## 三条评审线

- **Standards**：是否符合 ADR、既有 RFC、领域语言和项目约束；
- **Spec**：范围、行为与验收是否明确，技术设计是否遗漏、越界或暗中改写；
- **Architecture**：职责、依赖、接口、数据流和系统关系是否一致。

只报告实质问题和真实取舍。

## Spec 检查

- 范围与非目标是否明确；
- 正常、边界和失败行为是否足够清楚；
- 验收条件是否可观察、可判定；
- 产品决定是否仍需要实施者猜测；
- 技术探索是否还留有会改变范围的重要未知问题。

## 技术设计检查

- 是否覆盖适用的产品行为、约束和验收；
- 是否把产品假设当成技术决定；
- 是否存在尚未解决的重要技术选择；
- 是否具备足够清楚的验证切入点；
- RFC 集合的共享与切片边界是否完整，每条验收是否只有一个属主。

## 决定与修正

评审结果为通过、需要修订或拒绝。需要外部批准的决定，在取得批准前不得视为已接受。

Spec 与技术设计问题回到承载它们的 RFC 文件；没有 RFC 文件时回到工作项。状态、评审和批准证据回到 Proposal 或工作项；持久领域或架构决定在需要时通过 `domain-modeling` 进入 ADR。

修订共享 Spec 时，检查整个 RFC 集合，不只修改最先暴露问题的一份。

## 通过条件

- Standards、Spec 与 Architecture 没有未解决的实质问题；
- Spec 已经稳定；
- 每项验收都有技术设计与验证承接；
- RFC 集合的边界完整且不重复；
- 所需决定已解决并写回权威工件；
- 需要持久保存的决定已按约定记录；
- 实施不需要发明重要产品行为或架构。

通过后，把结果和决定依据记录在工作项，并按配置更新就绪状态。评审通过不自动构成批准或执行授权。

没有通过时，继续留在 Planning，修正拥有问题的工件并重新评审。普通实现细节可以保持开放。
