# Plan Review

确定被评审的 Proposal 或既有工作项、选定范围、适用产品合同与 Agent Note。工作项拥有本次产品行为和验收；跨工作项合同按需由独立 Spec 拥有。Agent Note 承载技术设计。评审整个规划集合，并把结果记录在同一工作项。

## 三条评审线

- **Standards**：是否符合现有权威决定、领域语言和项目约束；
- **Spec**：产品范围与验收是否明确，设计是否完整承接且没有遗漏、越界或暗中改写；
- **Architecture**：职责、依赖、接口、数据流和系统关系是否一致。

只报告实质问题和真实取舍。

## 产品合同检查

- 范围与非目标是否明确；
- 正常、边界和失败行为是否足够清楚；
- 标准、协议、安全策略、兼容边界和运维不变量是否写到能直接实现并验收的程度；
- 验收条件是否可观察、可判定；
- 产品决定是否仍需要实施者猜测；
- 是否混入了应由 Agent Note 拥有的技术设计；
- Spec 正文是否混入决策史或选择理由，修订记录是否只摘要合同变化；
- 技术探索是否还留有会改变范围的重要未知问题。

## 技术设计检查

- 是否能从工作项追溯到适用的产品要求，或引用明确的独立 Spec 修订与章节；
- 是否覆盖适用的产品行为和约束；
- 是否把产品假设当成技术决定；
- 是否存在尚未解决的重要技术选择；
- 是否具备足够清楚的验证切入点；
- 多份设计的边界是否完整且不互相矛盾；
- Agent Note 是否只拥有本决定的长期设计、真实备选与理由，批准证据是否留在工作项。

## 决定与修正

评审结果为通过、需要修订或拒绝。需要外部批准的决定，在取得批准前不得视为已接受。

按属主修正：

- 产品范围、行为与验收问题回到 Spec 或直接承载它的工作项；
- 本次规划的技术设计问题回到 Agent Note；引用输入的问题按项目配置反馈其属主；
- 状态、评审与批准证据回到 Proposal 或工作项；
- 领域术语问题通过 `domain-modeling` 写回领域资料，技术决定写回相关 Agent Note。

仅当提议为架构决定单独建档时，使用 `adr` 的准入条件检查反悔成本与真实权衡。其他 Agent Note 按项目部署后的 README 判断是否有长期设计价值。纯行为规则归产品合同；普通实现细节不因“重要”就自动生成 Note。

设计仍依赖临时产品假设时保持非权威。修订产品合同后，检查所有承接同一产品合同的设计，不只修改最先暴露问题的那一份。

## 通过条件

规划集合通过需要满足：

- Standards、Spec 与 Architecture 没有未解决的实质问题；
- 工作项产品合同或独立 Spec 已经稳定；
- 每项适用验收条件都有设计承接，或明确说明无需技术设计；
- 实施所需设计已按项目约定接受或批准；
- 设计与适用产品合同之间没有遗漏、越界或冲突；
- 所需决定已解决并写回权威工件；
- 需要持久保存的决定已按约定记录；
- 实施不需要发明重要产品行为或架构。

通过后，把结果和决定依据记录在工作项，并按配置更新就绪状态。评审通过不自动构成批准或执行授权。

没有通过时，继续留在 Planning，修正拥有问题的工件并重新评审。普通实现细节可以保持开放。
