# RFC 文件

RFC 文件同时承载 Spec 与技术设计。Spec 回答“做什么、哪些不做、怎样算完成”，技术设计回答“怎么实现”。两部分必须分节，避免技术方案暗中替产品做决定。

## 位置与生命周期

遵循项目工件注册表和既有 RFC 生命周期。RFC 在获得项目要求的评审与批准前保持非权威；被替代时保留与替代设计的关系。

项目没有格式时，可以使用：

```markdown
主题: <能力或切片>
当前修订: <修订标识>
状态: <项目约定的状态>

# <标题>

## 背景与目标
## Spec
### 产品范围
### 非目标
### 可观察行为
### 验收条件
## 技术事实与约束
## 技术设计
## 备选方案与取舍
## 迁移与兼容性
## 验证设计
## 未解决问题
```

按实际内容删去不适用章节，不为了完整感填写空壳。

## Spec

按 [spec.md](./spec.md) 写清产品合同。已有 PRD 可以提供背景，但 RFC 文件必须就地包含本次能力的 Spec。

## 技术设计

按需要解决会实质约束实现的内容：

- 系统边界与职责；
- 接口、协议、Schema 与持久化；
- 生命周期和失败行为；
- 兼容与迁移；
- 重要的安全、可靠性、性能或资源约束；
- 有意义的验证切入点。

普通实现细节留给实现阶段。设计发现产品缺口时，先修订同一 RFC 文件中的 Spec，再检查技术设计与关联 RFC 是否仍然成立。

## 探索草案

技术事实会影响产品范围时，可以先写 RFC 草案。草案必须区分 Spec 事实、临时假设和待决定问题；探索结论不能直接成为 Spec 或实施依据。

## RFC 集合

复杂能力可以拆成多份 RFC：

- 牵头 RFC 的 Spec 拥有共享目标、总体范围、共同验收和切片地图；
- 子 RFC 的 Spec 拥有本切片的范围与验收，文件内同时写对应技术设计并链接牵头 RFC；
- 共享 Spec 只写在牵头 RFC，切片 Spec 只写在对应子 RFC；
- 每条验收只有一个属主，集合合起来覆盖本次交付。

没有共享 Spec 的独立切片不必创建牵头 RFC。

## 定稿与评审条件

RFC 或 RFC 集合可以进入 Plan Review，需要满足：

- Spec 已经稳定；
- 临时假设与待决定问题不会影响实施范围；
- 重要技术决定已有结论，真实备选有推荐；
- 多份 RFC 的边界完整且没有重复属主；
- 验证设计足以覆盖每条验收；
- 实施不需要重新发明重要产品行为或技术决定。

准备好评审不等于已经接受、批准或取得执行授权。
