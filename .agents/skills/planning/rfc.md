# 技术设计

本文件提供技术设计的检查项，供 Planning 在 proposed Agent Note 中探索和定稿设计。Note 的位置与格式遵循项目配置。

设计可以早于产品合同定稿开始，但只有适用的工作项合同或独立 Spec 稳定后，才能被接受并成为实施依据。

## 位置与生命周期

遵循项目 Agent Notes README 的生命周期。proposed/implemented/rejected 反映交付结果，不代表批准。

设计在获得项目要求的评审与批准前保持非权威；被替代时保留与替代设计的关系。已交付 Note 的决定被推翻时，由新 Note 记录新决定，旧 Note 不改写成相反结论。

## 输入与承接关系

评审时应能从工作项确认：

- 承接的工作项产品要求，或独立 Spec 的修订及适用章节；
- 本设计负责的技术范围以及与同一产品合同下其他设计的边界。

一份产品合同可以拆给多份设计承接。设计不复制产品范围与验收正文；工作项建立要求与设计之间的链接。

## 探索草案

以下技术事实会影响产品范围时，可以先写探索草案：

- 上游能力和可用性；
- 成本、性能或资源上限；
- 兼容性与迁移可行性；
- 安全、可靠性或运维硬约束；
- 不同技术路线导致的产品体验差异。

探索草案必须区分已经确定的产品事实、临时假设和待决定问题。它输出可行性结论及其对产品范围的影响，把产品选择交回产品合同属主，不得自行定下产品行为。

探索草案不能作为实施依据。

## 技术设计

按需要解决会实质约束实现的内容：

- 系统边界与职责；
- 接口、协议、Schema 与持久化；
- 生命周期和失败行为；
- 兼容与迁移；
- 重要的安全、可靠性、性能或资源约束；
- 有意义的验证切入点。

普通实现细节留给实现阶段，不为完整感规定目录、类型或步骤。

设计不得扩大、缩小或改写适用产品合同。设计中发现产品缺口时，暂停相关部分的接受，先修订工作项或独立 Spec，再检查同一合同下其他设计是否受影响。

## 技术决定

在已同意的产品合同、既有架构和项目约束内，自主解决普通技术选择。重要备选存在真实取舍时，给出推荐与足够的评审理由。

需要产品、业务、兼容性、成本、风险、持久架构方向或其他价值判断时，交给相应决定权限，不把问题伪装成纯技术选择。

接受的决定形成或改变领域语言时，使用 `domain-modeling` 维护领域资料。需要为架构决定单独建档时，使用 `adr` 的准入条件判断；决定属于本设计时在同一 Note 中维护，可独立判断的新决定按项目 Note 规则记录。

## 定稿与评审条件

技术设计可以进入 Plan Review，需要满足：

- 适用的工作项产品合同或独立 Spec 已经稳定；
- 承接的工作项要求，或独立 Spec 的修订与章节明确；
- 方案足够解决重要技术决定；
- 重要备选有推荐；
- 需要外部权限的决定已明确；
- 验证切入点足够清楚；
- 实施不需要重新发现重要产品或技术决定。

准备好评审不等于已经接受或批准。
