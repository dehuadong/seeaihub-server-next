# Agent Note：运营不吊销客户的 API Key，客户侧只给密钥本身与客户语言的类别

## 问题

三处界面把平台内部的动作或科目摆到了不该看到它们的人面前。前两处的病根是"运营做不到"：**运营判断不了客户是否正在正常使用**一把密钥，也**拿不到要吊销的标识**——明文只在签发响应里出现一次，库里只有摘要，界面又不回显，于是那个"填标识再吊销"的表单实际上没有可用的输入。第三处（客户侧）违反 [`apps/web/AGENTS.md`](../../../../apps/web/AGENTS.md) 的约定：不要把系统内部逻辑带到客户侧。逐条看：

1. **运营端有"吊销 API Key"**：账户详情的 API Key 模块摆着一个"要吊销的密钥标识 + 吊销"表单，而它需要的输入运营根本拿不到（[控制台 Spec](../../../../docs/contracts/0001-admin-and-customer-consoles.md) C5）。这个表单是一把没有把手可握的枪。
2. **客户侧新建密钥时显示"密钥标识"**：它存在的唯一理由是让人抄下来去吊销，而客户吊销自己的密钥是在列表那一行点「吊销」，根本不需要抄标识。
3. **客户侧资金流水用「实际扣费」「资金调整」**：那是账本的分录类别（`capture`／`adjustment`）。「实际」是平台内部相对预授权说的；「资金调整」是运营做账的说法。客户看到的是"平台在跟我讲它自己的账"。

## 决定

产品规则归[控制台 Spec v18](../../../../docs/contracts/0001-admin-and-customer-consoles.md)（M5、C5、C8、V-C3、V-D14、V-D16），界面归属与文案归[设计 0011](../../../../docs/design/0011-console-information-architecture.md) §4.3、[设计 0014](../../../../docs/design/0014-customer-console-navigation-and-history.md) §3/§4。

- **运营端不再有吊销能力**：账户详情的 API Key 模块只剩"签发"与一次性明文（明文在**弹窗**里、只有密钥本身、关闭即清）。管理面**不再提供** `DELETE /api/v1/api-keys/{key_id}`——用户明确选了"界面与接口一起去掉"，不留界面上没有、接口还活着的能力。客户按自己会话吊销（`DELETE /v1/customer/api-keys/{key_id}`）是唯一的吊销路径。
- **客户侧新建密钥**：明文在**弹窗**里，内容只有密钥本身与"只显示这一次，现在抄走"的提示，按钮是「取消」；不再显示密钥标识。列表里的「吊销」按行操作、照旧先确认。
- **客户侧流水类别**用客户语言：`credit`「充值」、`capture`「扣费」、`adjustment`「运营调整」；筛选与汇总说明同步改。`capture`／`adjustment` 继续只作为接口取值与内部术语存在。
- **对账退款不写「运营调整」**：今天"只解除未结清预授权"的处置不产生资金流水（Spec `0002` §3），所以客户现在看不到这一类；「运营调整」是"已扣费之后的正式退款/人工调整"这一科目将来出现时的客户侧叫法。

## 备选方案

- **保留运营端吊销，只在文案上提醒"确认客户已停用"**：手术最小，但用户给的两条理由都没被解决——运营判不了、也拿不到标识，这个入口只会制造误操作。
- **保留吊销接口，只删界面**：能力还在（脚本、旧客户端、以后有人顺手接上），与"运营不吊销"的决定相反；用户已明确选择一起去掉。
- **运营端改成按账户"停用全部密钥"**：绕开"拿不到单个标识"的问题，但仍是运营替客户做决定，而且会让客户在不知道自己被停用的情况下调用失败；真需要时另立工作项。
- **客户侧明文继续显示密钥标识（供联系客服时报号）**：客户要报的可以是标签与创建时刻，标识是内部主键；留着它就得解释"这串是什么"，反而多一层内部概念。
- **类别继续叫「实际扣费」「资金调整」，在页面上加一句解释**：等于用一段说明把内部科目名讲给客户听——正是要避免的那种文案。
- **类别按金额方向显示「退款」「补扣」**：更具体，但"补扣"刺眼，而且一笔调整的语义是"运营动了余额"，方向由金额符号已经表达。

## 后果

- 运营少了一条止损手段：密钥泄露时只能由客户自己吊销。这是本次决定接受的代价（运营本来就判断不了客户是否在用，且拿不到标识）。真要运营侧处置，得先设计"停用账户／重新签发"这类产品动作，另行立项。
- 旧客户端的吊销调用会失败：管理面接口删除后，任何还按旧接口调用的脚本会拿到 404。开发阶段没有生产调用方，且用户明确要求去掉接口，因此不保留兼容层。
- 弹窗承载一次性明文：两个控制台都在关闭时清掉明文状态（不是隐藏），并由浏览器用例钉住"关闭→再进模块不出现"。
- 类别文案与接口取值分家：`capture`／`adjustment` 作为对客响应的取值不变，界面靠一张映射表说成"扣费／运营调整"；加类别时界面文案与用例两处都要改。
- 客户侧界面不再解释结算机制也不打内部取值：账单说明改成"扣费按实际入账时刻出现在这里"，空态不再出现 `credit` 字样。

## 验证

- `cargo test -p seeai-api --test http_contract -- --ignored --test-threads=1`：**180 passed**。`cases_public_surface` 的吊销用例改走**客户会话**（现在唯一的吊销路径）：吊销前可用、吊销后同一把明文立刻被拒（`invalid_api_key`）、不删行、重复吊销幂等且不改第一次时刻、审计只留一条、指向别人的密钥 404、没有会话 401；同时断言管理面旧路径 `DELETE /api/v1/api-keys/{key_id}` 已经是 404。未认证矩阵从 28 条减到 27 条（少了那条已删接口）。
- `cargo test -p seeai-application --all-features`：**156 passed**（去掉按标识吊销的端口方法后，四个测试替身同步更新）。
- `cd apps/web && npx playwright test`：全量**两次各 67 passed**。管理端断言 API Key 模块没有吊销按钮、没有"要吊销的密钥标识"、弹窗里只有密钥（不含"密钥标识"）、关闭即清且切回模块不再出现；客户侧断言新建明文在弹窗里、只有密钥、关闭即清；账单页断言三个类别名是「充值／扣费／运营调整」且页面上不出现"实际扣费""资金调整"。
- `cargo fmt --check` 通过；`cargo clippy -p seeai-application -p seeai-persistence -p seeai-api -p seeai-worker --all-targets --all-features -- -D warnings` 仍被既有的 `adapter-aihubmix` `single_element_loop` 挡住（该文件未改），放行该条后无告警。
- 一次 `cargo test -p seeai-application` 出现过一次未复现的失败（随后连续四次全绿，均为 156 passed）；没有留下失败输出，未能定位到具体用例，按偶发记录在此。
