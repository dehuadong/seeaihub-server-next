# Agent Note：账户名称唯一

## 问题

[账户名称独立于邮箱身份和路由标签](../../implemented/platform/2026-10-03-account-names-and-login-identities.md)把名称定成"属于账户、可重复，账户 id 才是唯一定位标识"，并已交付。用户随后指出：客户的账户名称**必须唯一，不能重名**。

重名的代价在运营侧最直接：列表与搜索按名称识别账户，两个同名账户会让"这个人是哪一个"重新变回靠 id 判断，名称作为识别手段的价值就没了。这个变更**部分取代**上文记录：名称的归属、生成来源、编辑权限、读投影与创建原子性仍然有效，被取代的只有"可重复"这一条。

## 决定

产品规则归[账户名称 Spec v3](../../../../docs/contracts/0003-account-names-and-login-identities.md)（N1、N3、N6），持久化与冲突处理归[设计 0015](../../../../docs/design/0015-account-names-and-login-identities.md) §1–§3、§5。

- **唯一性区分大小写**，覆盖全部账户（含平台账户那一行）：唯一索引建在 `name` 上，只有逐字符完全相同的名称才算撞名；`Star` 与 `star` 是两个名称。这是用户在同一天否掉"大小写不敏感"之后定的口径——先按 `lower(name)` 落地过一版，随后由迁移 `0030` 换成 `name`（见「后果」里的迁移顺序）。
- 名称**筛选**仍是大小写不敏感的子串匹配（运营输入小写也能找到大写的账户）；那是查找便利，与唯一性无关。
- **显式名称**：创建或改名撞上别的账户**完全相同**的名称返回 `409`，且不产生任何写入（账户、身份、资金、名称都保持原状）。改成自己当前的名称等于没改，不算冲突。
- **生成名称**：留空不再对应单一结果，而是一串候选，按顺序取第一个未被占用的——邮箱形式从 `<本地部分>_<id 前 4 位>` 起步，撞名把 id 片段加长为 6／8／12／16 位；`账户_<id 前 8 位>` 形式从 8 位起步加长为 8／12／16 位，并始终排在邮箱形式之后兜底。**生成路径不把冲突交给调用方**：客户自助注册不该因为"生成的短名字恰好被占用"而失败。
- **迁移 `0029` 先去重再建索引**：`0028` 回填出的 `账户_<id 前 8 位>` 本身不重名，但已经被人改成同名（或只差大小写）的开发库行要先拆开——保留最早那一行，其余各接上自己的 id 片段（当时的口径更严，按 `lower(name)` 分组）。随后 `0030` 把索引口径换到 `name`。唯一索引不会因回退代码而消失。

## 备选方案

- **只对精确相等的名称唯一**（索引建在 `name` 上）：**用户选了这个**。它不把 `Star` 与 `star` 当成一个名字——两者是两个名称，可以并存。
- **大小写不敏感的唯一**（索引建在 `lower(name)` 上）：一度按它落地，用户随即否掉（“大小写不敏感不好”）：同一个名字换个大小写就建不进来，而用户要的是"不能重名"而不是"不能形近"。换成区分大小写要改一条索引迁移（`0030`）。
- **在应用层做"查一遍再写"的唯一性判定，不建索引**：能给出友好的错误，但两个并发请求可以同时查到"没占用"再各自写入，重名仍会出现；判定必须有数据库约束兜底。
- **名称不唯一，改为在展示层给重名加后缀区分**：不动物化事实，但后缀只在某一处界面存在，导出、搜索与运营口头沟通仍会撞名。
- **给重名的后来者自动改名（例如追加 id 片段）**：调用方以为自己起的名字生效了，实际存的是另一个值，界面上"我填的名字去哪了"无法解释。只在**生成路径**上自动换候选是安全的，因为那个名字本来就是服务端起的。
- **生成时就固定用完整的 32 位账户 id**：唯一性几乎不依赖重试，但名称变成 `zhangsan_3f9a2b1c…` 这种不可读的长串，违背"名称用于识别"的初衷。改为只在撞名时加长片段。
- **名称唯一但区分大小写，同时禁止纯大小写差异**：相当于自己实现一遍大小写折叠，还漏掉 Unicode 的其他形近情况；数据库的 `lower()` 索引表达同一条规则且只有一个属主。

## 后果

- 名称唯一（逐字符完全相同）意味着"起名"可能失败：显式撞名返回 `409 name_taken`（与邮箱、账户绑定的 `conflict` 分开），生成路径不把冲突交给调用方——客户自助注册在首选名称被占用时由服务端换成更长的 id 片段，客户端无感。
- 唯一性是"**逐字符完全相同**"，不做 Unicode 形近折叠，也不折叠大小写（全角／半角、不同书写系统、`Star` 与 `star` 都算不同名称）；内容审核不在本次范围。运营仍要结合 id 与登录邮箱确认形近的名称。
- 迁移顺序是 `0029`（加 `lower(name)` 唯一索引，先把重名行拆开）→ `0030`（换成 `name` 上的唯一索引）。`0029` 的去重按 `lower(name)` 分组，比最终口径更严：它可能把"只差大小写"的行拆开过一版，那两行现在本可以并存，开发阶段不恢复（行仍带着自己的 id 片段，随时可改回来）。`0030` 只换索引，不重新去重——库经过 `0029` 已经不可能有完全相同的名称，所以它不会失败。
- 迁移 `0029` 会改掉重复组里除最早一行以外的名称（改成"截断后的名称 + 该行完整账户 id"，循环到不再有重名），这是开发库清理，不是产品行为；被改名的行仍带自己的 id 可辨识。
- 唯一索引存在之后，回退到"允许重名"的旧合同需要显式 `DROP INDEX ledger.accounts_name_key`；回退代码不需要，旧代码写的名称照样受约束。回退到"大小写不敏感"那版合同也一样要换索引（`lower(name)` 那一版已由 `0030` 换掉）。
- 生成候选最多尝试 8 次（邮箱 5 个 + `账户_` 形式 3 个），每次尝试是一次带唯一预检的写入事务；只在撞名时才会发生，正常路径仍是一次写入。
- 这次改动**部分取代**了[账户名称独立于邮箱身份和路由标签](2026-10-03-account-names-and-login-identities.md)：名称的归属、生成来源、编辑权限、读投影与创建原子性仍然有效，被取代的只有"名称可重复"。

## 验证

- `cargo test -p seeai-api --test http_contract -- --ignored --test-threads=1`：**180 passed**。名称那一组十二条覆盖：撞名创建与改名（**完全相同**才 `409`，错误码 `name_taken`）且账户总数不变、只差大小写的名称可以并存（唯一性区分大小写，管理端与客户侧各验一次）、改成自己当前的名称不算冲突、不存在优先返回 `404`、客户改自己被拒且原值不变、`name_taken` 与 `conflict`（重复邮箱、已绑定账户）是两个错误码、三条创建路径的生成名称在同一本地部分下互不相同、迁移去重（构造性撞名需要第二轮循环、长度上限不被顶穿、行数不变、索引落地并挡住重名）。
- `cargo test -p seeai-application --all-features`：**156 passed**（含候选序列的顺序、长度增长、去重与合法性）。
- `cd apps/web && npx playwright test`：全量**两次各 67 passed**（含建账户完全相同撞名留在表单、只差大小写的名称建成、改名相同名称被拒且保留原值、客户设置页改成别人名称被拒并保留原值）。
- `cargo fmt --check` 通过；`cargo clippy -p seeai-application -p seeai-persistence -p seeai-api -p seeai-worker --all-targets --all-features -- -D warnings` 仍被既有的 `adapter-aihubmix` `single_element_loop` 挡住（该文件未改），放行该条后无告警。
- 已知缺口（V10 的一条子句）：生成路径的"首选撞名 → 换下一位片段"没有**确定性**的端到端用例——账户 id 每行随机，合同层构造不出同片段碰撞（对照：迁移里"改名结果又撞上另一行"这种碰撞是可控的，所以那条能确定性验到）。候选序列由单测覆盖、唯一性与三条路径的生成结果由合同用例覆盖、迁移去重由真库用例覆盖；这条重试分支本身只有代码审阅把关。
