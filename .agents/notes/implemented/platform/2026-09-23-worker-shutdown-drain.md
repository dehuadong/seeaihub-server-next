# Agent Note：worker 终止信号改为优雅排空

## 问题

worker 收到终止信号时在 `select!` 的分支里直接返回：正在跑的那一轮——上游调用、计量落库、结算——连同它的 future 一起被丢掉。后果是 Job 留在"提交中"直到租约过期才被既有的过期租约回收捡起来：消费者要多等一个租约周期，运营侧还会看到一批本该正常的对账案例。编排系统滚动更新时会稳定复现这件事。

## 决定

信号只决定"**不再领下一轮**"：把手上那一轮的 future 等完再退出。做法是把 `run_once()` 的 future 固定住，内层 `select!` 只负责在信号到达时置位，外层等这一轮跑完再判断是否退出。

时限由**部署的宽限期**给，进程不自设超时，也不因为"排空太久"改写 Job 的处置；宽限期短于一次上游调用的最坏耗时是部署配置的问题。被强杀时未完成的 Job 仍由既有的过期租约回收兜住；已提交给上游而状态不确定的按既有口径进对账，**不自动重提**。容器 `SIGTERM` 与本地 Ctrl+C 走同一条路径。

## 备选方案

**保持硬退、靠租约过期兜底。** 落选：租约存在的意义是兜住进程崩溃这类意外，不是把正常的滚动更新变成"每个在飞 Job 都多等一个租约周期"；把可避免的等待写进常规路径，等于让运维动作稳定制造对账噪音。

**新增"把租约退回可再领取"的操作，收到信号时退回。** 落选：那需要新的仓储操作与状态迁移，而它解决的问题（本进程要退出了）用"把手上的活做完"就能解决；退回还会让上游已经受理的调用变成一次状态不确定的处置，比做完更差。

**给排空加进程内超时，超时就丢弃。** 落选：超时的正确来源是编排系统的宽限期——它知道强杀何时发生。进程再自设一个更短的超时，只会让"活没做完"发生得更早。

## 后果

滚动更新时不再制造"提交中"滞留的 Job。代价是退出会等待在飞的那一轮：一次上游调用最坏耗时就是最坏退出延迟，宽限期必须覆盖它，否则进程被强杀、退回租约过期那条路径。

## 验证

`cargo check -p seeai-worker --all-targets` 与 `cargo clippy -p seeai-worker --all-targets --all-features -- -D warnings` 通过。

**未覆盖**：验收要求的"给 worker 发信号后 Job 不滞留提交中"需要"慢上游 + 可编程信号"的端到端用例；现有夹具只起 API 进程，Windows 下也没有可编程的 Ctrl+C，因此这条没有实测。补齐的两条路：给夹具加"起 worker 进程 + 可编程信号 + 慢上游"的能力，或在能发信号的部署环境手工验一次。
