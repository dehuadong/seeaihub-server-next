# Agent Note：账实核对：按账户比对当前值与明细

## 问题

账户行上的当前值（`balance_microusd`、`held_microusd`）与它自己的明细（`ledger.entries` 的符号和、`ledger.holds` 里 active 行的金额和）本该是一体的：每一笔资金变动都同时改两边。但"本该"不等于"确实"——一次漏写、一次手工改库、一次半提交，都会让两个数从此对不上，而**在此之前没有任何东西会发现它**。上游让平台自担的成本、对账解除预授权这些情形也会让人去动账，动的过程同样可能出错。

## 决定

一个**只读的**按账户核查：核对 `balance = SUM(entries)` 与 `held = SUM(active holds)` 两条等式。任一不等即：

1. **建一条账户级对账案例**（`operations.reconciliation_cases`，`job_id` / `attempt_id` 为空、`account_id` 必填、`reason` 写明哪条等式断了与两边的数，状态沿用 `open`）；部分唯一索引 + `ON CONFLICT DO NOTHING` 保证**一个账户一直对不上只留一条**，返回值区分"新建 / 已有"；
2. **只有新建了案例才发一条平台侧告警**（与既有"新建对账案例即平台侧事件"同一口径；持续不符只留日志，不刷告警）。

实现落在 `crates/application/src/ledger_audit.rs`（`LedgerAuditor::audit_account` + `LedgerMismatch`）。**没有默认周期，也不扫全库**：管理员按账户触发 `POST /api/v1/accounts/{account_id}/ledger-audit`，触发即返回 `202`，核对在后台任务里执行——它不参与受理、结算或余额读取，也不该让管理员请求等它跑完。装配在 `apps/api`，它不读缓存，所以有没有 Redis 都能跑。

**它只发现、不改账。** 自动把余额改回去看着"自愈"，实际是把一次可能的作弊或漏写抹掉——那时再也没人知道为什么对不上。改账是人的决定。

占用那条等式与 `ledger.accounts.held_microusd` 的写入同事务维护（`0002` §2）；迁移 `0026` 给 active 预授权按账户建了部分索引，服务这条按账户的只读查询。

## 备选方案

**复用缓存对账那个任务。** 落选：两者比的是不同的东西——缓存对账比的是**库与缓存两份副本**（以库为准覆盖缓存），账实核对比的是**库里两组事实**。混在一个任务里，一旦有人把"对账"读成"对缓存"，就会以为账本已经有人看着了。

**不一致时自动把余额改成账本汇总。** 落选：见上——它会把"为什么对不上"这个信息一起抹掉，而那个信息正是这条任务存在的理由。

**默认每 15 分钟对全库重算。** 落选：请求耗时与库负载随历史流水条数增长，而账实不符不会自己好；改为按账户触发，生产规模增长后按账户分批调度（`0013` §5）。

**每轮不符都发一条告警。** 落选：一直没修的账户会反复刷同一条，把告警变成噪音；只在**新建**案例那一次发，配合"只留一条案例"，频率就由"问题数量"决定而不是由"轮数"决定。

**扩宽 `reconciliation_cases` 而不动它的可空性（例如给账户级案例造一个假 job）。** 落选：假 job 会让"这条案例关联哪次执行"永远说不清；放开 `job_id` / `attempt_id` 为可空反而更诚实——清单接口相应改成取案例自己那列（原来用 `INNER JOIN jobs` 取账户，账户级案例会被整条丢掉）。

## 后果

- 管理端 `GET /api/v1/reconciliation-cases` 的 `job_id` / `attempt_id` **可能为 null**（账户级案例），这是必要的代价：否则它在清单里根本看不见。
- 迁移 `0017` 顺带把既有两处**执行类**建案（`fail_job`、租约过期恢复）也补上了 `account_id`——原来那列是空的，而清单靠它取账户。
- **没有默认周期**：没人触发就不跑；"账实不符"的发现依赖运维按账户发起核查，不再有一个兜底的定时扫描。这是有意的：全库定时重算的成本随历史增长，而发现晚十几分钟的处置方式不变。
- **已知缺口**：账户不存在时的行为（查询返回 `None`、静默不建案）没有专门的自动化用例。

## 验证

模块单测五条：余额不符→建案+告警（载荷带两组数、一个数不改）、占用不符→建案+告警、两条都断→一条案例两句话、一致→零动作、已有未结案案例→不重复告警。合同用例五条（真 PostgreSQL）：改错余额→触发后案例出现且清单可见、告警带账户与两组数；改错 `held_microusd`→案例写清 active holds 与 held；一致时触发→案例与告警零动作、余额与条目一个不动；报出后再触发几次→余额与条目一个不变、未结案案例仍一条；正常启动的进程把余额改错、读一次账户、等两秒→一条案例都没有，显式触发后才出现。`cargo test -p seeai-application -p seeai-persistence` 149 passed / 0 failed。
