# Agent Note：账实核对：比对账本汇总与账户余额

## 问题

账本（`ledger.entries`）与账户余额（`ledger.accounts.balance_microusd`）本该是一体的：每一笔分录都同时改两边。但"本该"不等于"确实"——一次漏写、一次手工改库、一次半提交，都会让两个数从此对不上，而**在此之前没有任何东西会发现它**。上游让平台自担的成本、对账退款结案这些情形也会让人去动账，动的过程同样可能出错。

## 决定

新增一个**只读的**定时核对：按账户比对 `balance_microusd` 与 `SUM(entries.amount_microusd)`。两者不等即：

1. **建一条账户级对账案例**（`operations.reconciliation_cases`，`job_id`/`attempt_id` 为空、`account_id` 必填、`reason` 写明两个数，状态沿用 `open`）；部分唯一索引 + `ON CONFLICT DO NOTHING` 保证**一直对不上只留一条**，返回值区分"新建/已有"；
2. **只有新建了案例才发一条平台侧告警**（与既有"新建对账案例即平台侧事件"同一口径；持续不符只留一条日志，不刷告警）。

实现落在 `crates/application/src/ledger_audit.rs`（`LedgerAuditor` + `LedgerAuditPolicy`），装配在 `apps/api` 里紧挨既有的缓存对账——它不读缓存，所以有没有 Redis 都挂。配置项 `LEDGER_AUDIT_ENABLED`（默认开）与 `LEDGER_AUDIT_INTERVAL_MS`（默认 15 分钟）；关掉就根本不挂循环。

**它只发现、不改账。** 自动把余额改回去看着"自愈"，实际是把一次可能的作弊或漏写抹掉——那时再也没人知道为什么对不上。改账是人的决定。

比对口径用一条查询完成（`GROUP BY … HAVING 不相等`），因此**"余额非 0 却一条条目都没有"也报得出来**——那正是最容易漏掉的一类。

## 备选方案

**复用缓存对账那个任务。** 落选：两者比的是不同的东西——缓存对账比的是**库与缓存两份副本**（以库为准覆盖缓存），账实核对比的是**库里两个事实**。混在一个任务里，一旦有人把"对账"读成"对缓存"，就会以为账本已经有人看着了。

**不一致时自动把余额改成账本汇总。** 落选：见上——它会把"为什么对不上"这个信息一起抹掉，而那个信息正是这条任务存在的理由。

**每轮不符都发一条告警。** 落选：一直没修的账户会每 15 分钟刷一条，把告警变成噪音；只在**新建**案例那一次发，配合"只留一条案例"，频率就由"问题数量"决定而不是由"轮数"决定。

**扩宽 `reconciliation_cases` 而不动它的可空性（例如给账户级案例造一个假 job）。** 落选：假 job 会让"这条案例关联哪次执行"永远说不清；放开 `job_id`/`attempt_id` 为可空反而更诚实——清单接口相应改成取案例自己那列（原来用 `INNER JOIN jobs` 取账户，账户级案例会被整条丢掉）。

## 后果

- 管理端 `GET /api/v1/reconciliation-cases` 的 `job_id`/`attempt_id` **现在可能为 null**（账户级案例），这是必要的代价：否则它在清单里根本看不见。
- 迁移 `0017` 顺带把既有两处**执行类**建案（`fail_job`、租约过期恢复）也补上了 `account_id`——原来那列是空的，而清单靠它取账户。
- 默认**开**：这条任务的价值就是"不用人记得查"。
- **已知缺口**：`LEDGER_AUDIT_ENABLED=false` 的行为、多账户同轮、以及"长期不符时告警条数不随时间增长"都没有自动化用例（只测到案例不重复）。

## 验证

端到端三条：人为改错余额 ⇒ 案例出现且清单可见、告警带账户与两个数；一致时连跑六轮以上案例与告警条数不变、余额与条目一个不动，随后改错证明循环在这段窗口里是活的；报出后再跑几轮，余额仍是改错那个数、条目数不变、未结案案例仍只有一条。另有模块单测四条（不符→建案+告警、一致→零动作、已有未结案案例→不重复告警、周期必须为正）与告警载荷两条。空库端到端 `98 passed / 0 failed`。
