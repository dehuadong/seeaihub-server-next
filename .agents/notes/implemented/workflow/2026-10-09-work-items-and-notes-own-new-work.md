# Agent Note：工作项与 Agent Notes 拥有新工作的合同和设计

## 问题

Planning 技能已把工作项配置为本次行为与验收的属主，把 Agent Note 配置为长期技术设计与决定的属主，但项目文档入口、Issue 指南与 Notes 规则仍采用 Spec/RFC/ADR 分工。相同工作从不同入口会得到不同属主，Notes 又只能保存单次变更理由，不能完整承接技术内容。

旧设计还混有早期队列、重试、资产与端点规则。直接复制全文可能把旧机制重新变成现行规则。本次首次配置又把九份旧 Spec 复制成持续合同，用户明确纠正了这个归属选择。

## 决定

本记录拥有这次归属选择的理由与代价。当前位置和有效范围统一从[文档入口](../../../../docs/AGENTS.md#历史归属切换)读取；逐文件承接结果与缺口由[切换登记](../../../../docs/agents/document-ownership-transition.md)维护，不在本记录复制映射。

新工作的产品行为、范围、验收、评审与批准证据由已配置的 GitHub Proposal/Issue 持有，长期技术内容使用同主题 Agent Note。旧 Spec 原地归档，不复制到新合同目录；未来依赖工作在对应 Issue 确认适用行为和验收。历史归档与工作项承接是不同事实，未确认承接者的产品范围明确登记缺口。

技术设计与决定仍按范围完整承接和评审，再撤销对应旧权威。历史文件保留原文及替代关系，尚未完成的技术范围保持登记的过渡状态。不预建空目录或空记录。

本次修正项目入口、领域读取、跟踪器与 Notes 的归属规则，保留 GATES 的阶段授权、现有标签、三类 Note 分类、单一 GLOSSARY、Windows 相对路径校验修补和不生成 Note 索引的定制。配置不改变工作项状态，也不扩展工程实施授权。

## 备选方案

- 保持 Spec/RFC/ADR 独立拥有所有合同与设计：既有历史易读，但与已配置的新工作流程冲突，同一决定仍有两种去处；本次用户已选择切换，不采用。
- 把旧 Spec 复制到新的持续合同目录：曾用于保持原文引用，但形成了用户未选择的新合同体系；用户明确拒绝，移除新增副本，原始文件保留。
- 只声明所有旧技术内容已经完成承接：修改少，但安全、计量和执行机制仍可能缺少完整的新属主，不采用。
- 复制所有历史正文后立即撤权：能保留文字，却会把被后续决定取代的机制当成当前设计，并伪装未接受草案已通过，不采用。
- 旧 Spec 原地归档，行为由未来工作项明确；技术设计按范围完整承接、审阅后切换：维护成本较高，但能保留历史、区分未决范围并避免重复权威，采用。

## 后果

未来技术决定不再维护两份 RFC/ADR 与 Note。产品行为与验收由工作项持有，Note 完整拥有其技术范围和理由。读取历史链接仍能找到原文，但原文的接受状态不代替新工作的合同与批准。

切换不是一次目录改名。未完成范围仍有旧设计输入，依赖工作要先确认有效内容和接受证据；该成本明确记录，不能由自动补写理由或批准消除。本次独立评审只证明选定承接范围满足授权，不证明所有旧设计已接受或全部产品用例重新通过。

本记录在文档属主选择上取代[Spec/RFC 分离流程记录](2026-09-22-spec-rfc-planning-loop.md)与[旧治理记录](2026-09-23-document-governance-and-adr-gates.md)的相应部分；产品／技术职责分离、非权威探索、PRD 按需、统一入口、准入条件和既有历史验证仍保留其原意。

## 验证

本次 Standards 与 Spec 独立评审先指出上传重试阶段、签名机制和迁移代价的漏项，以及 Note 中变量名、计价示例与错误解析的过时描述。补齐并与代码核对后，第 2 轮两轴通过。旧内容撤权安排在该评审之后。

首次评审曾核对九份副本与历史正文等价，但该证据不证明用户选择了新增合同目录。本次按用户纠正移除副本，九份原始 Spec 保留正文及历史状态，新工作的产品合同承接不冒称完成。模型类型、上传与 AIHubMix Notes 复用已有真实备选及产品交付证据；没有通过文档修正新增产品能力。

机械检查按[Git 规则](../../../../docs/agents/git.md)运行 Note 格式、本地链接、历史正文保留、删除范围、引用范围、代码仅注释差异及 `git diff --check`；本次更正也按两轴评审核对。结果在交付报告给出。源码只改注释，SQL 历史迁移不改写。Rust、真实数据库和浏览器产品测试不因归属修正重跑；没有调用 Provider 或 OSS。
