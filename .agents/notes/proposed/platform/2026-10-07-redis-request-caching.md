# Agent Note：Redis 请求缓存：必要性判据与 API Key 身份缓存设计

## 问题

一次成功的同步图片请求在请求路径上至少走 8 次 PostgreSQL 往返：认证 API Key、HTTP 层同键预查、用例内第二次同键预查、读候选与模型并发名额、读路由策略、受理事务、提交声明事务、结算事务，再加收尾后为刷新缓存发生的余额读取（[direct_execution.rs](../../../../crates/application/src/direct_execution.rs)）。`user_tag` 策略再加一次标签读，候选声明了成本币种再加一次汇率读。

三处现状与直觉不符，必须先说清，否则必要性判断会落空。

**第一，余额缓存没有任何请求路径读者。** `AccelerationService::read_balance` 只在写穿时的版本闸门与对账器里被调用（[lib.rs](../../../../crates/application/src/lib.rs)）；管理员与客户端的余额读一律走数据库。所以 `user_balance:<account_id>` 今天只产生成本：每次资金变动后多一次 `SELECT` 加两次 Redis 往返，全部 await 在响应路径上。

**第二，PostgreSQL 连接池固定 10 条，生产改不了。** 它是字面量，出现在第一次提交里，只设了 `max_connections`；`min_connections`、`acquire_timeout`、`idle_timeout`、`max_lifetime` 全取 sqlx 缺省（0 / 30 秒 / 10 分钟 / 30 分钟），见 [main.rs](../../../../apps/api/src/main.rs) 与 [persistence](../../../../crates/persistence/src/lib.rs)。仓库里没有这个数的推导记录，也没有配置项。缺省的 30 秒获取超时意味着池满时请求**排队等待**而不是快速失败。

**第三，本机缺省并发上限是 4，不是 10。** `GENERATION_EXECUTION_SLOTS` 由内存预算推导（2 GiB ÷ 437 MiB），`GENERATION_READ_SLOTS` 与 `GENERATION_SEND_SLOTS` 各 64。也就是说：稳态下同时在飞的执行只有 4 个，每个只在数据库阶段占连接，上游调用期间不占。**缺省配置下连接池不是先饱和的那个资源。**

已有的性能证据只有一次本机单次观测（`docs/verification/synchronous-gateway.md`）：并发 8、假上游固定 200 毫秒时 20.13 请求/秒，网关净耗时 p50 82.4 毫秒、p95 97.0、p99 119.7。这是**延迟受限**的观测（8 ÷ 0.370 秒 ≈ 21.6 请求/秒，与实测吻合），不是容量观测：没有发布版构建、没有生产环境、没有池等待时间、没有把并发推高到吞吐不再上升。**哪个资源先饱和，没有实测。**

## 提案

### 1 必要性判据

缓存有两个正当用途，都要能用数字说话：

- **复用贵的计算结果**：一次读要 JOIN 多张表、传输并解析大段 JSON 正文，而结果在多次请求间相同；
- **压低权威库的访问总量**：不是为了单次延迟，而是为了让权威库的资源（连接、CPU）不随请求量线性增长。

「不常变动」这个性质的作用**不是**「可以容忍旧值」，而是「**可以在每次变动时同步失效**」。变动越少，写穿失效越便宜；变动频繁的对象反而不能这样缓存。所以缓存的设计基础是**写穿失效**，TTL 只做兜底。这一条直接推翻了「缓存必然带来陈旧窗口」的前提。

必要性要同时满足三条：

1. 这个读在请求路径上且频率高；
2. 它的结果能同步失效——写入口集中、变动低频；
3. 被省下的资源**确实是瓶颈**，有实测的饱和证据。

第 3 条现在没有证据，取证方式由[受理路径的容量测量](./2026-10-09-admission-path-capacity-measurement.md)承接。所以本轮的结论是**有条件成立**：设计可以做，启用前必须先有饱和证据；而在取得证据之前，先做第 7 节的故障边界，它不依赖任何产品决定。

### 2 API Key 身份缓存

这一项**不需要任何产品语义变化**，现行 Spec 的「吊销立刻生效」原样成立。

**缓存两个键，都用现成的读写命令：**

- `auth:key:<sha256>` → `account_id`，TTL = `CACHE_API_KEY_TTL_SECONDS`（默认 60）。值只需要 `account_id`：认证返回的 `key_id` 在生成与上传路径上都没有下游读者。
- `auth:revoked:<sha256>` → `1`，TTL = `CACHE_API_KEY_REVOKE_TTL_SECONDS`（默认 600，必须 ≥ 上者）。

**每个请求的读顺序：**

1. 读 `auth:revoked:<sha256>`。命中即 401，不查库。
2. 未命中，读 `auth:key:<sha256>`。命中即用它的 `account_id`，**不查库**。
3. 都未命中，查 PostgreSQL 现有那条语句。有行则写 `auth:key`；无行（不存在或已吊销）则写 `auth:revoked`，TTL 取短值（默认 10 秒）。

两个键合并成一次往返：给 `CacheStore` 加一条**通用的**批量读 `get_many(&[&str]) -> Vec<Option<String>>`。它不认识「Key」「吊销」「余额」，只是批量读，所以不把业务语义带进实现方。

**吊销的顺序：**

1. 在 PostgreSQL 事务里写 `revoked_at`（现有语句，改成 `RETURNING id, key_hash`），提交。
2. 写 `auth:revoked:<sha256>`，并删 `auth:key:<sha256>`。
3. **第 2 步成功之前不返回成功。** 失败就把错误回给客户；客户重试时第 1 步幂等，第 2 步再写一次。

**为什么没有窗口。** 每个请求都读 `auth:revoked`。吊销成功后这个键就在 Redis 里，所有实例下一次请求立刻看到。「撤销成功」以 Redis 标记写成功为前提，所以「撤销成功后新认证不得接受该 Key」成立，Spec `0001` 的 V-D16 与 V-C4 不用改一个字。

**为什么旧回填覆盖不了吊销。** 请求路径的回填只写 `auth:key`，从不写 `auth:revoked`。一个在吊销前读出、吊销后才回填的旧身份，会与已存在的吊销标记并存；读顺序先看标记，仍然拒绝。所以这里**不需要版本号、不需要 CAS、不需要 Lua**——两个键分开就够了。这是本设计与提案草案最主要的差别。

**Redis 故障时安全。** 读不到 Redis 时两个键都当未命中，回落到 PostgreSQL 那条点查；行为退化成今天的样子，正确性不变。Redis 隔离的实例同理。

**剩下的真实缺口**（写进设计、不需要用户裁定，因为它是纯技术参数）：PostgreSQL 已提交、Redis 标记写失败、且调用方放弃重试时，`auth:key` 可能还在，该 Key 会继续被接受直到它的 TTL 到期。这是跨两个系统的写无法原子的固有缺口。收窄办法两条：`auth:key` 的 TTL 取短（默认 60 秒就是最坏残留时间）；对账器按现有 `run_reconciler` 的模式定期扫最近被吊销的 Key，确保标记存在，把缺口从 TTL 缩到对账周期，且不依赖客户重试。

**顺带压掉枚举压力。** 随机 Key 全部未命中、每次都查库，是今天一个真实的放大点。第 3 步的负缓存把它挡在 Redis 里，TTL 取短，所以新签发的 Key 不会被误拒（要误拒得先有人猜中那个哈希）。

**收益的量级。** 认证查询从「每请求一次」降到「每把 Key 每 60 秒一次」，且跨实例共享一份。代价是每请求一次 Redis 批量读，替代一次 PostgreSQL 点查——往返次数不变，PG 负载大幅下降。

**要同步修订的设计属主。** [运维基线设计](../../../../docs/design/0009-operational-baseline.md) §4 现在写的是「缓存里只能放『密钥标识 → 账户』的映射，**吊销判定仍然每次读库**——加速不能改变判据」。本设计把吊销事实的读取点从「每请求查库」移到「Redis 标记，数据库兜底」，判据本身不变、窗口为零，但**机制确实换了**。所以那一句必须随本设计一起修订，不能只改代码。这是本设计接受前要过的第 4 项修订（提案 #83 的 D4）。

### 3 候选、策略与账户标签

这是**最贵**的那次读：一条 6 表 JOIN，把每个候选的 `capability_schema`、`carrier_schema`、`parameter_mapping`、`restrictions` 与定价列一起传回来，每请求重做一遍解析（[persistence](../../../../crates/persistence/src/lib.rs)）。

设计：给 `publication.gateway_models` 加一列 `catalog_version`，**所有影响该模型受理的写入口在同一事务里递增它**——发布、模型启停、**模型并发名额改动**、Offering 与 Channel 启停、动态公式与单位成本、Price Plan、策略新增改删、账户标签改动。请求路径先做一次紧凑读（读这一行加当前生效修订标识），比对版本；命中就用 Redis 里的序列化候选正文，替代 JOIN、正文传输与解析。

版本读仍访问数据库，所以这里**不宣传成免查库**；省下的是最贵的那段工作。这条查询比 JOIN 便宜一个量级，必要性判据的第 1、2 条成立，第 3 条待测。

**并发名额必须进版本。** 它挂在模型行上、由 `PATCH /api/v1/gateway-models/{name}` 与发布命令两条路径改，改了即时生效、不进修订。缓存整份候选集时只改名额而不改版本，就会读回旧名额。

策略与账户标签并入同一个版本：`routing.route_policies` 已有 `version` 列可以直接用；`ledger.accounts` 的标签要单独加版本列，不能借 `updated_at`（那是余额缓存的新鲜度判据，`set_account_tag` 有意不动它）。

### 4 汇率

汇率不能只靠写失效：未来的 `effective_at` 会在没有新写入的情况下自己生效。紧凑读里必须带「当前生效汇率标识 + 数据库时间 + 下一生效时点」，缓存只存不可变值。本地时间、TTL 和通知都不决定资金汇率。

### 5 余额缓存

今天的余额缓存没有读者，所以**必要性为零**。两条路：

- **删掉写穿与对账**，资金事务不再返回余额快照；响应路径少一次 `SELECT` 与两次 Redis 往返。这是确定能拿到的收益。
- **保留并给它一个读者**（受理前预检）。但预检的收益没有实测，且缓存说不足仍必须由数据库确认，省下的是「渠道咨询锁 + 一次注定失败的条件更新 + 事务回滚」，不是往返次数。

本轮建议走第一条。预检作为独立的待测项，不在本设计内。

### 6 并发计数不进缓存

「账户 × 网关模型」的在飞计数必须与建 Job 在同一个事务、同一把账户行锁下做，放到 Redis 就脱离了这个串行化点。它的上界就是名额本身（几条索引行），误判两个方向都伤：偏高会拒掉合法请求，偏低会放开上游并发。渠道全局容量同理。真要优化，方向是数据库侧维护计数行，不是 Redis。

### 7 Redis 故障边界（前置项）

现在建连时持锁、单次 200 毫秒超时、失败即丢连接、下一个请求再连一次，没有退避、没有共享截止时刻、没有恢复探测。一旦 Redis 进入请求路径（第 2、3、4 节），这些成本会乘在每个请求上。所以这一项要**先于**任何请求路径缓存落地：一次操作的总时限包含连接锁等待与建连，失败进入有上限的退避区间，恢复只允许一次探测，其余请求回退数据库。

## 备选方案

**API Key：进程内有效期窗口（提案草案的 D1）。** 落选。它把「吊销多快生效」变成产品语义变化，要升 Spec `0001` 的版本；而它换来的只是把一次 PostgreSQL 点查换成一次 Redis 往返——往返次数没变，Redis 那一层省不下东西，只带出「删除失败、实例隔离、旧回填」整套协议。第 2 节的两键方案在同一收益下不需要改任何产品合同。

**API Key：单键加 TTL 失效。** 落选。吊销只删一个键时，一个在吊销前读出、吊销后才回填的旧身份会把它写回来，且没有第二处可以拦住。两键分离正是为了消掉这个竞态。

**API Key：版本比较加原子 CAS。** 落选。提案草案用「身份版本 + 原子版本比较」防旧回填；两键分离后不需要版本号，也不需要给 `CacheStore` 加带业务语义的原子命令。

**API Key：把吊销标记做成永久键。** 落选。标记 TTL 只要不短于身份 TTL，身份先过期，标记就没有必要永久留着占内存。

**候选：只用发布通知失效，不做版本读。** 落选。通知会丢；停用与改价必须写入即生效，正确性不能挂在通知上。

**候选：缓存 live 表而不做版本。** 落选。`formula`、`cost_unit_price_microusd`、`offerings.enabled`、`channels.enabled`、`max_concurrent_jobs` 都不在修订快照里，只按修订标识缓存会读回旧值。

**余额：保留写穿并等预检批准。** 落选（本轮）。它今天没有读者，成本确定、收益未测。

**在飞计数：Redis 计数器加对账。** 落选。脱离受理事务的串行化点后必须保留数据库计数当权威，缓存省不下东西。

**先扩容连接池，再谈缓存。** 落选为替代方案，但**要先做**：连接池是可配置化加一次测量的成本，比任何缓存都便宜。只有在池已经放大、而 PostgreSQL 自身仍是瓶颈时，减少访问量才有意义。把池做成配置项并给出缺省值，属于实现细节，由实现阶段处理。

## 验收条件

1. 有效 Key 命中缓存时，请求路径上**没有** `identity.api_keys` 的查询；用假上游与假 Redis，按 SQL 计数比对命中前后。
2. 吊销成功后，第二个实例的新请求立刻被拒（不等待任何 TTL）；覆盖「吊销与回填交错」「回填晚于吊销到达」两种交错。
3. 假 Redis 停掉、或指向不可达地址时，认证回落到 PostgreSQL，正确性不变；已有合同套件在缓存启用与关闭两态下结果逐位相同。
4. `auth:key` 的 TTL 到期后，下一次请求重新查库；`auth:revoked` 的 TTL 不短于它。
5. 对账器能把「PostgreSQL 已吊销、Redis 缺标记」的 Key 补上标记，且留下可查的痕迹。
6. 随机 Key 连打不落到 PostgreSQL（负缓存生效），且不影响之后真实签发的 Key。
7. 候选缓存命中时不再执行那条 6 表 JOIN；只改模型并发名额、不改任何其它配置时，缓存必须失效。
8. 未来 `effective_at` 的汇率到点自动生效，不需要新写入，也不依赖 TTL 或通知。
9. 缓存关闭时，全部验收条件对应的行为与今天逐位相同。
10. Redis 不可达时，单次操作的总时限包含连接锁等待，且不出现每请求依次重连的等待放大；有并发故障用例。

## 风险

- **跨系统写的缺口**：PostgreSQL 已提交、Redis 标记写失败且调用方放弃重试时，被吊销的 Key 会继续可用到 `auth:key` TTL 到期。靠短 TTL 与对账器补标记收窄，不能完全消除。这是引入任何共享缓存都要付的代价。
- **Redis 键名含 Key 哈希**：键名会出现在慢日志、`MONITOR` 与内存快照里。哈希本身不能当凭据用（认证比对的是哈希），风险与 `identity.api_keys.key_hash` 列同级，但要把 Redis 的访问面按数据库同级看待。
- **`catalog_version` 的维护完整性**：任何影响受理的写入口漏了递增，就会读回旧配置。这是本设计最容易出错的地方，必须逐入口核对，并用「改一处、验一处」的用例守住。
- **必要性尚未证实**：缺省配置下并发上限是 4，连接池是 10，先饱和的资源没有实测。缓存可能解决的不是真正的瓶颈。测量由[受理路径的容量测量](./2026-10-09-admission-path-capacity-measurement.md)承接；第 7 节与连接池可配置化应先于第 2、3 节落地。
- **多一个失败路径**：Redis 从「只在公开鉴权端点计数」变成请求路径上的依赖。第 7 节是它的必要前提。
