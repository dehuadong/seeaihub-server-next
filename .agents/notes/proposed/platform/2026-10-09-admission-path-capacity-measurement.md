# Agent Note：受理路径的容量测量：先定饱和资源，再定缓存

## 问题

提案 #83 要按「Redis 减少请求路径的数据库工作」立范围，但**先饱和的是哪个资源没有实测**。三个数放在一起时不支持「数据库是瓶颈」这个前提：

- 本机缺省同时在飞的执行是 **4**（`GENERATION_EXECUTION_SLOTS` 由内存预算推导：2 GiB ÷ 437 MiB）；读取与发送名额各 64。
- PostgreSQL 连接池是 **10**，写在代码里的字面量，只设了 `max_connections`；`acquire_timeout` 取 sqlx 缺省的 30 秒，池满时请求**排队等待**而不是快速失败。
- 唯一一次留档的负载观测（`docs/verification/synchronous-gateway.md`）是并发 8、假上游固定 200 毫秒下的 **20.13 请求/秒**。它是**延迟受限**的：8 ÷ 0.370 秒 ≈ 21.6，与实测吻合。也就是说吞吐完全由「并发数 ÷ 延迟」决定，没有推到任何资源饱和。

同步请求从头到尾占着一个执行名额，所以每副本吞吐约等于「执行名额 ÷ 上游延迟」。真实图像生成是秒到几十秒级（上游超时缺省是基础 180 秒、每多一张加 30 秒），因此单副本实际吞吐远低于 1 请求/秒。**在这个速率下连接池是闲的。**

而连接池是**全进程共用**的：生成、上传、控制台与管理端读走同一个 `PgHubRepository` 的同一个池。所以「池够不够」不是只看生成路径就能回答的。

结论：在定缓存范围之前，必须先把「哪个资源先饱和」测出来。这组测量是提案 #83 的必要性证据，不是缓存实现的一部分。

## 提案

### 1 测量要回答的一个问题

**在目标吞吐下，先饱和的是哪一个资源？** 候选有五个：

| 候选资源 | 观测方式 |
| --- | --- |
| 本机执行名额 | 名额占用率、容量拒绝次数 |
| PostgreSQL 连接池 | 池等待时间与等待次数、借出数峰值 |
| PostgreSQL 本身 | 每语句耗时与调用次数、后端连接数峰值、等待事件 |
| 本机 CPU 与内存带宽 | 进程与整机占用 |
| 上游延迟本身 | 固定延迟下的总耗时拆分 |

### 2 要量的五个数

1. **每请求的 SQL 条数与语句分类**：认证、同键预查（两次）、候选与并发名额、路由策略、账户标签、汇率、受理事务、提交声明事务、结算事务、收尾后的余额读取，各计一条。
2. **每请求的 PostgreSQL 连接占用时间**：从借出到归还；以及池的等待时间与等待次数。
3. **PostgreSQL 侧**：每语句的耗时与调用次数；后端连接数峰值。
4. **端到端**：固定上游延迟下，把并发推高到吞吐不再上升，记录拐点，以及拐点处前四个候选资源各自的值。
5. **非生成流量**：控制台与管理端的读能否与生成请求在同一个池上互相排队；单独压它时池与 PG 的表现。

### 3 采集方式

- **SQL 条数**：仓里已经有能数语句的用例（`direct_sql_count_does_not_grow_with_provider_wait` 的做法），把它做成请求级计数即可，不引入新依赖。
- **池等待**：`PgPool` 自带 `size()` 与 `num_idle()`；等待时间要在借出前后各取一次时钟。插桩位置与是否常驻属于实现细节，实现阶段定。
- **PostgreSQL 侧**：有 `pg_stat_statements` 就用它；没有就退回 `pg_stat_activity` 采样加逐语句 `EXPLAIN (ANALYZE, BUFFERS)`。
- **负载**：沿用 `cases_performance_baseline` 的夹具——进程内假上游、一次性库、真 API 进程；把上游延迟参数化。全部 `#[ignore]`，离线，零计费调用。
- **构建**：用 `cargo test` 测试 profile 与本机 debug 构建就够，因为要判断的是「哪个资源先饱和」，不是「容量是多少」。发布版构建与生产环境不在本轮。

### 4 负载矩阵

| 维度 | 取值 | 理由 |
| --- | --- | --- |
| 上游延迟 | 0 毫秒、200 毫秒、2 秒 | 0 毫秒把网关自身暴露成瓶颈；200 毫秒与留档可比；2 秒接近真实量级 |
| 并发 | 1、4、8、16、32、64 | 覆盖缺省执行名额 4 与读取名额 64 两个台阶 |
| 每档样本 | 120 个成功请求 | 与留档的网关耗时拆分同口径，够算 p50/p95/p99 |

### 5 记录位置

`docs/verification/` 下新增一份留档，表格式沿用 `synchronous-gateway.md` 的「验收记录」。用例**不写性能断言**：它只打印观测，阈值由部署目标定。

## 备选方案

**直接调大连接池看效果。** 落选：池是可配置化加一次测量就能改的，但改了之后仍然不知道限住吞吐的是池、PG 还是执行名额；把池调大还可能让 PG 自己先饱和。

**用生产环境压测。** 落选：本轮没有生产环境，且不该对生产发起负载。

**只数 SQL 条数。** 落选：条数不等于占用时间。少量长查询与大量短查询是两种不同的瓶颈，只数条数会把后者误判成前者。

**引入外部压测工具（wrk、k6）。** 落选：多一个依赖，而且拿不到进程内的池等待与名额占用。

**把这组测量并进缓存设计记录。** 落选：两条记录的问题、生命周期与结论不同——本记录产出数字，缓存设计产出机制；一条变成 `implemented` 时另一条还是 `proposed`。两条互相链接。

## 验收条件

1. 第 2 节的五个数都有留档，并注明构建 profile、机器、上游延迟与并发。
2. 吞吐—并发曲线在测试的取值范围内出现拐点，且拐点处四个候选资源的值都记下来。
3. 结论写成一句可判定的话：「在 X 并发、Y 上游延迟下，先饱和的是 Z」。
4. 判定不出来时，写明缺哪个数、为什么缺，不给出替代性结论。
5. 非生成流量那一条单独给出结论：共用同一个池时能否与生成请求互相排队。
6. 全部离线、零计费调用；用例带 `#[ignore]` 并写明前置条件。

## 风险

- **本机的数不代表生产**：debug 构建、WSL2、单机 PostgreSQL。所以本记录只支持「哪个资源先饱和」这一个结论，不支持容量规划。
- **单机测不出多副本**：多个 API 副本共享一台 PostgreSQL 时的总连接数与池的竞争，本组测量覆盖不到。
- **插桩可能改变被测对象**：请求级计数与池计时都在热路径上。实现时要把插桩开销本身量一次，否则测到的是插桩。
- **测量结果可能推翻缓存范围**：如果先饱和的是执行名额或本机 CPU，提案 #83 的大部分缓存条目就不该做。这是本记录要接受的结论，不是失败。
