# Agent Note：管理员读余额：读数据库那一行，不读缓存

## 问题

提案 #13 第 4 条要"管理员能查看余额"，但这条读一直没有落点：`/api/v1/accounts` 只有建账户、充值、发 Key 三个写入口，运营要看余额只能直查 `ledger.accounts`。同时账户余额已经有了 Redis 缓存（P4），缓存的值可能滞后，也可能是对账任务覆盖写回的——如果这条读走缓存，它在"账实是否相符"这个问题上就等于拿被怀疑的一方作证。

## 提案

新增管理员读 `GET /api/v1/accounts/{account_id}`，返回 `balance_microusd` 与 `updated_at`，两者都取 `ledger.accounts` 那一行；账户不存在返回 404，没有管理员凭证返回 401。读取路径刻意**不经过加速层**：即使缓存可用、即使缓存里是新鲜值，这条读也直接查库。缓存只服务受理期的余额预检（省一次查库），不服务"查看账目"。

计划：应用层加一个端口方法（读账户当前余额与写入时刻）与 `AccountsService::read_balance`；持久层把已有的私有读实现暴露成该端口；API 加路由与 handler；补一条端到端用例，其中先把缓存改成一个错的数，断言读回来的仍是库里的值。

## 备选方案

**让这条读走缓存、只在未命中时回源数据库。** 落选：缓存的新鲜度只够支撑"提前拒绝"这种无副作用的判断，不够支撑"告诉运营账上还有多少钱"。这条读的用途正是对账，读到一个滞后或来自对账覆盖的数会把账实不符读成账实相符，而错的那一侧恰好是权威数据源的对立面。

**在响应里附带缓存里的值供对照。** 落选：响应里出现两个"余额"，调用方要自己判断哪个能信；不一致时正确的动作是查库与对账，不是把两个数一起抛给读的人。

## 验收条件

- 管理员读到 `balance_microusd` 与 `updated_at`；余额与 `ledger.accounts` 逐位一致；
- 缓存里被写成别的数时，读回来的仍是库里的值；
- 无管理员凭证 401，账户不存在 404；
- 用例：`the_admin_reads_a_balance_from_the_database_not_the_cache`。

## 风险

只做读取，不改任何写路径，也不给对客暴露余额。与工单 #9 的"账目可见"诉求同源，实施只做这一处；成本护栏不在本范围。
