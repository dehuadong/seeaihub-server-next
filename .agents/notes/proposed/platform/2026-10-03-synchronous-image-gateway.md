# Agent Note：同步图片网关取消业务载荷持久化

## 问题

[此前图片透传记录](../../implemented/platform/2026-09-20-images-pass-through-without-asset-storage.md)禁止自有资产托管、公开异步与图片文件落盘，但保留内部 Job/Worker 执行。因此 [API](../../../../apps/api/src/main.rs) 仍创建持久 Job 并轮询结果；[Persistence](../../../../crates/persistence/src/lib.rs) 写入原生参数及结果图片 JSON，[Worker](../../../../apps/worker/src/main.rs) 领取并串行执行。data URL 与 `b64_json` 仍可成为 PostgreSQL 业务载荷，随 WAL、复制及读取产生额外成本。

用户明确本项目是参数处理、渠道转发、费用计算与响应归一的网关，不需要保存请求或结果。该方向部分替代此前透传方案的内部队列与结果持久化选择，仍保留对客同步、结果原形、无资产身份及有证据才结算的边界。此前记录仍是其历史理由与验证证据的属主。

## 提案

长期合同由[同步网关 Spec](../../../../docs/contracts/0005-synchronous-image-gateway.md)拥有，执行、容量、Adapter 接口和迁移由[同步网关 RFC](../../../../docs/design/0017-synchronous-image-gateway.md)拥有。本记录仅保存选择理由、备选及有意承担的后果；不创建未经确认的永久 ADR。接受后应在此前透传记录补充本记录链接，标明其内部执行选择被部分取代。

直接执行使请求不必跨进程恢复，能够取消为 Worker 保存正文及 API 反复查询大结果的要求。PostgreSQL 继续拥有预授权、证据、金额与异常事实；将 payload 与账务命令分成不同类型，比“约定不要写字段”更容易阻止再次引入正文存储。

现有表与 Job/Attempt 标识继续支撑账本和用量关联，避免仅为更名重做财务迁移。Client 复用、只准备选中候选、字节共享和有界执行是本次可独立验证的效率来源。采用有界缓冲是因为计量可能位于图片之后，正常成功又要求先确认结算；不能用未经证实的全流式或零复制承诺替代账务边界。

整改的技术细节由[资源、收尾与传输设计](../../../../docs/design/0018-synchronous-gateway-remediation.md)拥有，已随 Spec v2 生效。补充选择的理由是：账务收尾必须与执行 owner、响应交付分开；响应 Body 结束不能证明传输缓冲释放。先把事实交接、存储与传输许可分开，比修改几个局部条件更能覆盖竞争与崩溃窗口。

## 备选方案

- 保留 Worker 生成，但把正文改存 Redis/MQ：仍保存业务载荷，还引入另一套恢复及容量问题，不满足用户边界。
- API 直接调用且完全不保存执行事实：无法可靠保留占用、价格快照、资金幂等和提交未知处置，不采用。
- 上游结果立即转发，再异步记账：可降低首字节等待，但正常成功与结算分离，崩溃可能已交付却漏扣或重复扣，不作为本期方案。
- 完整请求与结果进入对象存储：仍违反不保留业务载荷要求，不采用。
- 直接调用、内存载荷、最小事实与异常对账：满足用户方向，接受不能恢复图片和部分崩溃窗口无法自动核实费用的代价，作为推荐。
- 只给响应 Body 增加计时或分块：不能终止已经进入 Hyper 写缓冲的图片，也不能证明许可释放，不用于整改的发送保证。
- 自管连接的关闭期限：使用公开依赖接口即可实施，首期 HTTP/2 整连接关闭会影响其他流，保守持有发送资源会降低吞吐；推荐先以可验证上界为依据，逐流隔离另作验证。
- 为不存在的旧摘要保留历史查找密钥：会把一次性数据处置变成长期必填配置，不采用。当前身份是无密钥 SHA，将来若真的接入旧库，按一次性数据处理而不是长期兼容层。

## 验收条件

可判定验收统一见 [Spec §8](../../../../docs/contracts/0005-synchronous-image-gateway.md#8-验收条件)，性能与故障证据切入点见 [RFC §8](../../../../docs/design/0017-synchronous-image-gateway.md#8-验证与性能证据)。历史清理须覆盖已存在的内联参数与结果，不能只证明新请求没有写入。

本次整改的故障证据与剩余验收覆盖见[整改验证清单](../../../../docs/verification/synchronous-gateway-remediation.md)。清单是执行步骤，不表示实现已通过，也不沿用此前局部测试为整改完成证据。

## 整改的机制证据

整改范围固定代码基线 `606398ade1cd1c414320a5ec68cd295c88d5bf24`。传输机制以本机内存 socket/epoll 实验确认：只监视关闭事件的连接不消费 pipeline 字节，对端 `SHUT_WR` 可观察到 `RDHUP`，`ONESHOT` 不重复触发。这是操作系统机制证据，不替代 Hyper/Axum 集成与真实 socket 故障验证，后者记在[整改验证清单](../../../../docs/verification/synchronous-gateway-remediation.md)。

## 风险

数据库与 Provider 没有共同事务，提交声明后发送前、Provider 接受后句柄入库前、读到证据后持久化前都有信息缺口。取消载荷持久化后这些缺口不能通过重放正文修复；未知请求保留占用并转对账，可能需要人工解除，无法核实的成本不能冒充零。

成功响应丢失后没有结果重放，客户端需理解同键只防重复收费。Provider 已产生费用而客户端未收到图片时的收费边界见已接受 Spec §7；补偿采用正式资金调整，不能把传输失败当作渠道免费。

未知任务保留渠道容量可防止超过上游真实并发，但可能降低可用性；须有缺口告警和可信人工处置，不能以自动过期伪装已经结束。历史载荷可能残留在备份与 WAL，破坏性清理有运维成本，且删列后的回退必须继续满足无载荷合同。

最大响应及解析/编码副本可能让单执行安全预留达到数百 MiB 或更高，最终并发需按真实上界计算。首期连接关闭监视限定 Linux；HTTP/2 同连接其他流与维护窗口影响需在草案审批时确认。
