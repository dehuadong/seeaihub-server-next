# Agent Notes

本目录保存 Agent Notes：与工程工作相关的重要决定与交付理由，记录问题、真实取舍与实际交付结果。浏览 [索引](./INDEX.md)，分类以 [项目配置](./config.json) 为唯一来源；需要新记录时参考 [后备模板](./templates/record.md)。

## 记录范围与信息归属

新部署的 Agent Notes 由仓库管理根目录的 `.agents/notes/` 统一承载。管理根目录依项目指令和既有工件注册确定，不随当前子项目工作目录改变；Git 顶层仅作未明确配置时的查找依据。多上下文共用根级工件注册入口和记录系统，不在各子项目重复初始化。已登记的历史位置保持归属，整合迁移需明确授权。

上下文映射负责领域边界，记录分类仅由本目录 config.json 管理，不自动一项目一分类。上下文 ADR 已拥有的决定由记录引用，不复制其正文。注册的位置值以管理根目录为基准，普通 Markdown 链接仍相对所在文件解析。

本仓库的工件职责边界（见 `docs/agents/artifacts.md`）：决策的权威位置是 `docs/adr/`，ADR 拥有决策正文；独立技术设计 RFC 位于 `docs/design/`；本目录记录工程变更、交付理由与验证，引用相关 ADR 或 RFC 而不复制其正文。

影响行为、架构、接口、跨模块约定、数据/协议/配置格式、测试策略或重要技术选择的工程变更，应在同一 PR 或同一交付变更中新增、更新或关联已有记录。重大未来工作先形成提案。分类不是工件类型，也不是必须逐一生成的产物。

已有 Proposal、RFC、Spec、ADR、Issue 等充分承载决定与依据时，继续由它拥有信息，无需重新综合。需要独立保存重要决定或交付取舍时才创建本目录记录，并引用相关提案或工作项。Proposal 的内容与工作状态按项目已配置的跟踪机制管理，本目录不复制提案正文或承担工单进度。

历史上同一文件兼任提案和记录时，沿用项目注册的归属及状态映射，分别识别工作进展、批准和交付生命周期；重新注册不自动拆分、迁移或增加竞争状态字段。

纯机械编辑、链接修复、格式整理和索引生成属于文档维护，按请求直接处理并检查，不启动一轮工程规划或新建提案。若文档修改实质改变工程合同，按所改变的合同处理。记录制度不新增批准或执行权限。

## 目录与项目分类

路径为 `{lifecycle}/{category}/YYYY-MM-DD-topic-slug.md`。日期表示首次提出日期，无法核实时使用建档日期并说明。文件名在所有生命周期及分类中唯一，不因状态变化重命名；主题使用小写英文和连字符。分类目录按需创建。

config.json 使用如下结构，示例类别仅展示字段，不是默认分类：

```json
{
  "version": 1,
  "categories": [
    { "id": "example", "name": "项目类别名称", "scope": "覆盖的实际交付对象" }
  ]
}
```

初始化优先复用项目分类；没有时依据项目能力、系统对象和工程范围提出方案，由用户确认。记录选择一个主要类别，跨类别通过链接关联。新增类别只改配置，脚本读取它，索引生成类别视图；不在 README 另存类别清单。空 categories 可初始化空项目，创建首份记录前必须确定类别。

本仓库已确认的分类为 `domain`（领域语义与规则）、`platform`（平台基础设施与运行时）、`workflow`（仓库工程约定与工具），名称与覆盖范围以 [config.json](./config.json) 为唯一来源。

## 生命周期与批准

| 路径与 status | 含义 |
| --- | --- |
| proposed | 尚未交付或部分交付；可以待审阅，也可以已批准 |
| implemented | 所记录范围已交付并完成必要验证 |
| rejected | 已否决，保留原因和相关取舍 |

批准依据与生命周期分开，采用项目已有约定；执行授权另行判断。批准不能自动进入 implemented，测试通过也不能自动批准。没有充分交付证据时保留 proposed。

使用 UTF-8 Markdown，一行一个 `key: value` 的简单元数据块，不使用嵌套 YAML 或引号语法。必填 title、status、created、updated、approval；implemented 另需 verification，rejected 另需 reason。额外项目字段允许保留。日期为 YYYY-MM-DD，created 与文件名一致，updated 在实质变更时更新。

正文优先采用项目已有格式，脚本不固定章节标题。尚未交付的决定记录说明问题、选择、理由、影响和未决事项，范围与验收优先引用对应工作项；已交付记录改述实际决定、结果、代价和验证依据。字段可指向正文说明，正文使用相对 Markdown 链接关联文件。不能虚构批准、测试结果或原本未讨论的替代方案。

状态变化在同一变更中完成文件移动、status 更新、按实际结果改写正文及入站/出站链接修正，再生成索引。检查目标冲突；拒绝时记录原因。已交付决定被替代仍留在 implemented，明确失效范围，并与替代记录双向链接；引用 implemented 记录前仍须检查其替代说明。初期不设自动归档或删除。

## 总体方案、阶段和模块工程

总体提案拥有目标、范围、阶段划分、依赖和阶段验收条件，链接阶段工作项及模块工程。提案与进度由已配置的跟踪器管理，本地 Markdown 也需明确配置，不在每层复制合同。

模块工程按需执行 Discuss → Plan → Implement → Verify，必要时在相关范围内多次循环。阶段完成还需要集成和阶段验收，不能只累加模块完成状态。覆盖总体范围的变更记录在全部交付前保持 proposed，独立下级记录可以先进入 implemented；Proposal 本身使用跟踪器工作状态。只有包含独立重要决定的模块才另建记录，不机械要求一模块一 Note。

## 更新责任与文件边界

同一决定的事实修正和必要补充更新原记录；可独立判断的新选择另建记录；实质改变已接受决定时新建替代记录，保留历史理由。记录不积累会议纪要、完整实现清单或测试日志。

| 阶段 | 动作 |
| --- | --- |
| Discuss / Plan | 查已有合同与相关记录，形成必要提案和未决事项 |
| Plan Review | 结论写回本次 Proposal 或既有工作项，记录仅关联涉及本决定的评审与批准依据 |
| Implement | 同一变更维护事实与引用，重大合同变化返回 Planning |
| Implementation Review | 核对范围、实现与记录一致，必要维护已完成 |
| Verify | 验证交付范围，据实迁移生命周期并引用证据 |

只检查相关记录，不要求每个任务遍历全部历史。日常文档治理不受上表的工程阶段序列约束。

## 索引与检查

从项目根目录运行，使用 Node.js，无第三方依赖：

```sh
node scripts/decisions/update-index.mjs
node scripts/decisions/check.mjs
```

INDEX.md 由配置和记录生成，不手动编辑。检查覆盖配置、目录与生命周期一致性、必要元数据、日期、文件名唯一性、内联本地链接目标及索引新鲜度。关联工作项的本地链接同样检查；远程目标、标题锚点、批准真实性、实际交付是否充分及替代关系语义仍由审阅判断。代码示例中的链接不检查。

脚本不自动批准、迁移状态或修改决定，不默认安装 CI、钩子或外部发布。初始化资源部署后属于项目副本；重复 setup 不覆盖，升级时保留项目分类和定制。
