# Agent Notes

本目录保存 Agent Notes：与工程工作相关的重要决定与交付理由，记录问题、真实取舍与实际交付结果。清单就是 `{生命周期}/{分类}/` 目录树本身，按目录浏览或仓库搜索查找，不生成集中索引；分类以 [项目配置](./config.json) 为唯一来源。**正文写法（含代码注释）遵循 [`docs/AGENTS.md`](../../docs/AGENTS.md) 的写作规则与 slop 清单**——本文件只规定记录特有的目录、生命周期与文件格式。

## 记录范围与信息归属

新部署的 Agent Notes 由仓库管理根目录的 `.agents/notes/` 统一承载。管理根目录依项目指令和既有工件注册确定，不随当前子项目工作目录改变；Git 顶层仅作未明确配置时的查找依据。多上下文共用根级工件注册入口和记录系统，不在各子项目重复初始化。已登记的历史位置保持归属，整合迁移需明确授权。

上下文映射负责领域边界，记录分类仅由本目录 config.json 管理，不自动一项目一分类。上下文 ADR 已拥有的决定由记录引用，不复制其正文。注册的位置值以管理根目录为基准，普通 Markdown 链接仍相对所在文件解析。

本仓库的工件职责边界（见 `docs/agents/artifacts.md`）：决策的权威位置是 `docs/adr/`，ADR 拥有决策正文；独立技术设计 RFC 位于 `docs/design/`；本目录记录工程变更、交付理由与验证，引用相关 ADR 或 RFC 而不复制其正文。

影响行为、架构、接口、跨模块约定、数据/协议/配置格式、测试策略或重要技术选择的工程变更，应在同一 PR 或同一交付变更中新增、更新或关联已有记录。重大未来工作先形成提案。分类不是工件类型，也不是必须逐一生成的产物。

已有 Proposal、RFC、Spec、ADR、Issue 等充分承载决定与依据时，继续由它拥有信息，无需重新综合。需要独立保存重要决定或交付取舍时才创建本目录记录，并引用相关提案或工作项。Proposal 的内容与工作状态按项目已配置的跟踪机制管理，本目录不复制提案正文或承担工单进度，也不积攒会议纪要、完整实现清单与测试日志——过程留在提交历史与工作项里。

历史上同一文件兼任提案和记录时，沿用项目注册的归属及状态映射，分别识别工作进展、批准和交付生命周期；重新注册不自动拆分、迁移或增加竞争状态字段。

纯机械编辑、链接修复和格式整理属于文档维护，按请求直接处理并检查，不启动一轮工程规划或新建提案。若文档修改实质改变工程合同，按所改变的合同处理。记录制度不新增批准或执行权限。

## 目录与项目分类

路径为 `{lifecycle}/{category}/YYYY-MM-DD-topic-slug.md`。日期表示首次提出日期，无法核实时使用建档日期并说明。文件名在所有生命周期及分类中唯一，不因状态变化重命名；主题使用小写英文和连字符。分类目录按需创建。

config.json 使用如下结构，示例类别仅展示字段，不是默认分类：

```json
{
  "version": 1,
  "categories": [
    { "id": "example", "name": "项目类别名称", "scope": "覆盖的实际交付对象" }
  ]
}
```

初始化优先复用项目分类；没有时依据项目能力、系统对象和工程范围提出方案，由用户确认。记录选择一个主要类别，跨类别通过链接关联。新增类别只改配置，脚本读取它并据此校验记录目录；不在 README 另存类别清单。空 categories 可初始化空项目，创建首份记录前必须确定类别。

本仓库已确认的分类为 `domain`（领域语义与规则）、`platform`（平台基础设施与运行时）、`workflow`（仓库工程约定与工具），名称与覆盖范围以 [config.json](./config.json) 为唯一来源。

## 生命周期

路径顶层就是生命周期，记录随状态在文件夹之间移动，`status` 必须与所在文件夹一致：

| 生命周期 | 含义 | 进入条件 | 离开条件 |
| --- | --- | --- | --- |
| proposed | 尚未交付或部分交付；可以待审阅，也可以已批准 | 新记录一律从这里开始 | 交付并完成必要验证后移入 implemented；被否决时移入 rejected |
| implemented | 所记录范围已交付并完成必要验证 | 交付证据齐备：用例、命令、实测留档 | 被完全取代时按「更新责任与文件边界」合并进持有该决定的记录；不因时间久远或价值降低而移动 |
| rejected | 已否决，保留原因和相关取舍 | 提案或候选决定被否决，且其理由仍能避免一次容易重犯的错误 | 不移动；理由已无指导价值时，连同入站链接一并删除 |

批准依据与生命周期分开，采用项目已有约定；执行授权另行判断。批准不能自动进入 implemented，测试通过也不能自动批准；批准与验证证据必须如实，不能虚构。没有充分交付证据时保留 proposed。

移动生命周期是一次内容改写，不是改一个字段：

- proposed → implemented：`## 提案` 改写成现在时的 `## 决定`，`## 验收条件` 与 `## 风险` 折入 `## 后果`（或折入 `## 验证`，写现在锁住该行为的东西），计划与迁移步骤换成实际交付的事实；
- proposed → rejected：否决结论写进 `status` 与 `reason`，正文按提案期原样冻结；
- 已交付决定被替代仍留在 implemented，写清失效范围，并与替代记录双向链接；引用 implemented 记录前仍须检查它的替代说明。初期不设自动归档或删除。

移动的形态变化在同一变更里做完：文件移动到目标生命周期目录、`status` 更新、按实际结果改写正文、修正入站与出站链接，最后运行检查。发现记录之间冲突时先解决冲突再移动；被否决时把原因记进 `reason` 与正文。

## 文件格式

每份记录的文件内形态固定，由 `node scripts/decisions/check.mjs` 强制。格式建立于 2026-09-22：定义格式的同一变更改造了整个语料库，不设过渡期，也不容忍两套格式并存。

### 元数据块

文件开头是元数据块，一行一个 `key: value`，不使用嵌套 YAML 或引号语法，只用下面这套键、按这个顺序：

```markdown
---
title: 记录标题
status: proposed
created: YYYY-MM-DD
updated: YYYY-MM-DD
approval: 批准依据
verification: 验证证据
reason: 一句话否决理由
---
```

- `status` 取 `proposed` / `implemented` / `rejected`，与所在文件夹一致；
- `created` 与文件名日期一致，`updated` 在实质变更时更新、且不早于 `created`；
- `approval` 必填，指到批准依据；批准不等于执行授权；
- `verification` 只出现在 implemented，一行指到验证证据（用例名、命令、留档位置）；证据本身写在正文 `## 验证`；
- `reason` 只出现在 rejected，一句话写清否决结论。

字段是索引，不是正文：要展开的内容写进正文，字段保持一行。

### 标题与正文骨架

元数据块之后的第一个非空行是标题，冒号后的文字与 `title` 逐字一致：

```markdown
# Agent Note：记录标题
```

正文第一个章节固定为 `## 问题`：动机与约束，不用读者先看方案。其余固定章节按生命周期取用下面这套规范名；真正独特的技术章节（数据结构、协议形状、迁移、落点等）可以自由插在固定章节之间。

| 生命周期 | 除 `## 问题` 外的必需章节 |
| --- | --- |
| proposed | `## 提案`（拟议的变更，可用将来时，含计划与迁移步骤）、`## 备选方案`、`## 验收条件`（什么可观察状态算完成）、`## 风险`（可能出错的事与本变更有意放弃的东西） |
| implemented | `## 决定`（现在时描述已交付的事实）、`## 备选方案`、`## 后果`（换来了什么、付了什么代价、留下哪些限制与未决事项）、`## 验证` |
| rejected | `## 备选方案`；原本是提案的保留 `## 提案` 等提案期章节，原本是决定候选的保留原结构 |

implemented 里不得出现 `## 提案`、`## 计划`、`## 迁移计划`、`## 验收条件`——这些是提案期用语，交付后要改写成现在时的事实。

### 备选方案必须写

每份记录都要有 `## 备选方案`：真实考虑过、并落选的方案与原因，每个方案一段、加粗起头，争议大的用 `### 为什么不选 <方案>`。不为了填章节编造方案——记录决定击败了什么，才能防止同一场争论重来。

格式建立日（2026-09-22，含）之前创建、且无法从既有内容还原备选方案的记录，用下面这条注释代替该章节：

```markdown
<!-- agent-note-format: alternatives-not-recorded (pre-format Agent Note) -->
```

该注释对 2026-09-22 之后创建的记录无效，检查会拒绝。

## 总体方案、阶段和模块工程

总体提案拥有目标、范围、阶段划分、依赖和阶段验收条件，链接阶段工作项及模块工程。提案与进度由已配置的跟踪器管理，本地 Markdown 也需明确配置，不在每层复制合同。

模块工程按需执行 Discuss → Plan → Implement → Verify，必要时在相关范围内多次循环。阶段完成还需要集成和阶段验收，不能只累加模块完成状态。覆盖总体范围的变更记录在全部交付前保持 proposed，独立下级记录可以先进入 implemented；Proposal 本身使用跟踪器工作状态。只有包含独立重要决定的模块才另建记录，不机械要求一模块一 Note。

## 更新责任与文件边界

同一决定的事实修正和必要补充更新原记录；可独立判断的新选择另建记录；实质改变已接受决定时新建替代记录，保留历史理由。完全取代时可以把旧记录并入持有该决定的记录并删除原文件，前提是当前记录已经收下旧记录独有的理由、备选方案、影响与验证，入站链接全部修好；部分取代不算，两条记录互相链接并各自更新仍然适用的事实。

| 阶段 | 动作 |
| --- | --- |
| Discuss / Plan | 查已有合同与相关记录，形成必要提案和未决事项 |
| Plan Review | 结论写回本次 Proposal 或既有工作项，记录仅关联涉及本决定的评审与批准依据 |
| Implement | 同一变更维护事实与引用，重大合同变化返回 Planning |
| Implementation Review | 核对范围、实现与记录一致，必要维护已完成 |
| Verify | 验证交付范围，据实迁移生命周期并引用证据 |

只检查相关记录，不要求每个任务遍历全部历史。日常文档治理不受上表的工程阶段序列约束。

## 检查

不生成集中索引：`{生命周期}/{分类}/` 目录树就是清单，浏览目录或搜索仓库负责内容发现。生成索引会重复文件名已编码的生命周期、分类、日期与标题，还会让互不相关的分支争用同一个文件，因此本目录只保留人工维护的入口（本文件）和检查脚本；根目录出现 `INDEX.md` 会被检查拒绝。

从项目根目录运行，使用 Node.js，无第三方依赖：

```sh
node scripts/decisions/check.mjs
```

检查覆盖配置、目录与生命周期一致性、元数据块（键集合、键序、各生命周期的必填键）、文件格式（标题行与 `title` 一致、首个章节、各生命周期的规范章节与禁用章节、备选方案或豁免注释）、日期、文件名唯一性及内联本地链接目标。关联工作项的本地链接同样检查；远程目标、标题锚点、批准真实性、实际交付是否充分、备选方案是否属实及替代关系语义仍由审阅判断。代码示例中的链接不检查。

脚本不自动批准、迁移状态或修改决定，不默认安装 CI、钩子或外部发布。初始化资源部署后属于项目副本；重复 setup 不覆盖，升级时保留项目分类和定制。
