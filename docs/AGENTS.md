# 文档标准

本文件是仓库文档的统一入口：定义文档分层、位置、职责与写法。它适用于 `docs/`、`.agents/notes/`、根 `AGENTS.md`、`GLOSSARY.md`，也适用于 `crates/`、`apps/` 里的注释与 doc comment。

## 文档分层

| 文档 | 位置 | 职责 | 不承载 |
| --- | --- | --- | --- |
| PRD | 用户指定或项目既有位置 | 初步产品意图、用户问题、目标与价值 | 可实施的工程合同 |
| Proposal / Ticket | GitHub Issues，配置见 [`issue-tracker.md`](agents/issue-tracker.md) | 本次范围、产品行为与验收、工作状态、评审与批准证据，及设计链接 | 长期技术设计与决定正文 |
| 历史 Spec / RFC / ADR | `docs/specs/`、`docs/design/`、`docs/adr/` | 冻结历史来源；已切换范围及尚未承接的旧属主见下文归属入口 | 新主题、新工作的默认实施依据 |
| 新 RFC / ADR | 不启用独立文件；技术提案、设计、决定归 Agent Note | 同一决定复用其 Note | 第二份技术权威 |
| 领域词汇表 | 根 `GLOSSARY.md` | 领域术语与定义 | 设计、目录索引与实施状态 |
| 架构治理 | `docs/architecture.md` | 分层职责、依赖方向、边界规则与扩展纪律 | 文件、表、端点与迁移清单（由源码、`migrations/` 与各模块文档承载）；持久决定 |
| 渠道事实 | `docs/facts/` | 已核实的渠道结论 | 平台规则、设计理由与调用流水 |
| 调研 | `docs/research/` | 结论、事实、推论、待确认与来源 | 运行时合同 |
| 验证清单 | `docs/verification/` | 执行步骤与证据；旧验收引用仅作历史依据 | 工作项拥有的新工作验收合同 |
| 部署与配置参考 | `docs/operations/` | 怎么跑起来、上生产与全部配置项：开发环境、生产部署、容器、每个变量的缺省与生产取值 | 使用教程（归 `docs/tutorials/`）；产品、技术或架构决定 |
| 使用教程 | `docs/tutorials/` | 管理、运营与运维**按场景怎么使用**这套系统：操作步骤、失败处置与验证 | 部署与配置参考（归 `docs/operations/`）；产品行为与技术决定（归上表登记的属主） |
| Agent Note | `.agents/notes/`；分类与路径由 [`config.json`](../.agents/notes/config.json) 及 [`README.md`](../.agents/notes/README.md) 定义 | 面向后续维护代码的 Agent 与人类维护者，保存长期有价值的技术提案与决定、真实备选、理由及后果 | 产品合同、工作状态和已有权威设计全文 |
| 外部原始材料 | `out-reference/` | 上游快照、样本与其他背景证据 | 工程合同、运行时输入与项目决定 |
| Agent 指令与技能 | 各级 `AGENTS.md`、`.agents/skills/` | Agent 行为护栏与工作方法 | 产品与运行时合同 |

文件有真实内容时才创建，优先更新同一主题的既有文件。Agent Note 的生命周期与骨架见 [`.agents/notes/README.md`](../.agents/notes/README.md)，Proposal 与 Ticket 的状态见 [`issue-tracker.md`](agents/issue-tracker.md)，提交与推送见 [`git.md`](agents/git.md)。

## 一个事实一个家

每个事实由负责它的那一层写清楚，其他地方只链接。新工作的产品行为、范围、验收、评审与批准证据归 Proposal/Issue；长期技术设计与决定归 Agent Note。跨工作项沿用的行为由相关工作项明确适用范围，不因历史 Spec 存在而默认继承。提交历史记录变更过程。

## 历史归属切换

管理根为本仓库根目录，子项目也读取本入口。逐文件的旧属主、新属主、适用范围、切换结果及未决影响由[归属切换登记](agents/document-ownership-transition.md)拥有。旧目录冻结，不接收新主题，不删除或搬移历史文件。登记为未完成切换的范围暂保留旧属主，后续工作必须先核对有效内容、补齐新属主与评审，不得默认沿用旧工件。

旧 Spec 原地保留为归档资料，原生效修订及批准状态只说明历史。新工作从 Proposal/Issue 取得行为与验收，不另建独立 Spec 目录，也不把旧 Spec 复制成新的产品合同。历史行为尚无已确认工作项承接时，归属登记写清缺口；依赖工作先在对应 Issue 确认适用范围和验收，不能把归档视为已经完成承接。规划技能中的独立 Spec 分支在本项目不启用。

- **一份文档的读者与用途决定它写多细**：别替别层写它该写的细节，原地用链接指过去；文档类型不扩大它的范围。
- **每种文档只对自己的主题穷尽**：参考资料可以把自身范围内的内容列全，别处的不列。
- **机器能生成或校验的清单不手抄**（迁移列表、路由表、测试清单、包与端点目录），链接到源码或生成物。
- **写文档的顺序**：先确定归属与位置，再确定这一层该写多细；不属于这一层的内容搬回它的家，原地留链接。

## 写作规则

- **写当前状态**：变更过程归提交与 Agent Notes；Spec 可保留只说明合同变化的修订记录。正文点出仍然生效的内容，不写「已删除」「已改为」这类迁移叙述，也不写代码在栈里的位置。
- **保留完整命题**：删形容词、重复与叙述之前，先确认每个事实都还在——动作与执行者、条件与时序、必须／可以／绝不、负向保证与例外、归属、副作用、失败方式与后果。字少不等于更好。
- **注释只补充代码无法表达、读者必须知道的行为与约束**：公开 API 的 doc comment 写清调用方依赖的合同；内部注释只写必要的非显然信息，不复述代码、不记录推理过程。长期设计理由可链接适用的已交付 Agent Note；不链接 ADR、RFC／设计文档、Proposal、Ticket 或 Issue。
- **一个段落一行**：用编辑器软换行；表格、代码块与列表保持原有格式。
- **推论与事实分开**：可核实的事实标出处（用例名、命令、留档位置、上游文档），推论、估计与待确认明确标注，不写成既成事实。
- **合同与记录按属主闭环**：工作项写全本次范围、行为、验收、评审与批准证据；长期设计与理由写进 Agent Note，工作项链接其适用范围。仓库工件使用相对链接，不反向复制工作项范围或评审流水；既有历史外部引用保留。旧 Spec 链接仅提供历史依据，不授予新工作的实施授权。历史代码引用使用 tag 或提交。
- **用能指向具体对象的词**：写端点、字段、类型、表、命令或行为本身，不写要读者猜的隐喻。「面」「形状」「契约」这类词先问一遍有没有更准的名字；`契约` 只留给调用方、实现方、生产者或消费者真正依赖的前提、后置条件、不变量与兼容承诺。本仓库已经定义的术语（如 `Runtime Revision`、`Job`）直接用。
- **不写推理过程**：不写实现步骤叙述、显然分支的推导、测试走演、评审过程与被否掉的局部备选。留下结论、合同与日后还会用到的理由。
- **不写状态标注**：「已实现」「未来会…」会随代码腐坏；状态由目录、清单与代码本身承载。
- **强调节制**：加粗只给改变行为的那一句或真正要紧的对比；到处都是重点等于没有重点。
- **中文简体**，术语与 [`GLOSSARY.md`](../GLOSSARY.md) 一致；同一概念只用一个词，不为了换花样改称呼。
- **一节只讲一件事**：一段塞进好几条规则与括号补充时，拆开，或把细节降级到它的家。

## 按位置补什么

同一套规则落到不同位置，要写的东西不一样；缺了才补，不缺就不要加。

| 位置 | 要写清的 |
| --- | --- |
| 模块头与公开项的 doc comment | 模块的职责、依赖与非显然的架构选择（长期理由按需链接适用的已交付 Agent Note）；公开函数的行为差别、错误与失败方式、副作用、所有权与时机、取消与持久化 |
| 其他注释 | 不变量、并发与顺序、所有权、安全边界、会让人意外的失败行为；不显然的地方写一句就够 |
| 测试 | 只解释不显然的测试设计：为什么用这个 fixture、为什么这么断言、为什么绕开平台；删掉步骤走查与用例清单 |
| README 与 `docs/` 正文 | 消费方要遵守的合同：配置、语义、失败、限制、扩展点 |
| Agent Note | 独有的理由、机制、备选方案、后果与验证证据，见 `.agents/notes/README.md` |
| 技能与 agent 指令（`.agents/skills/`、各级 `AGENTS.md`） | 行为护栏与明确的范围限制；保持简短，链接真相来源 |
| 对客串、日志与诊断信息 | 措辞就是行为：改动要跑拥有该输出的用例。诊断要点名失败的主体或路径、违反的规则与怎么改 |

## slop 清单

审文档与注释时逐条找：

- 同一条规则出现在两处：搜一个特征短语，留一个家，其余链接。
- 历史写进了不该写历史的层：正文陈述当前事实，历史链接到它的家。
- 正文或图里写实现状态（「已实现」「未来：…」）。
- 手抄目录、JSDoc 或测试清单，而源码或生成器才是权威。
- 推理过程：实现步骤叙述、显然分支的证明、测试走演、被否掉的局部备选。
- 注释复述代码：把控制流、字段名或类型已经表达的事再讲一遍。
- 同一段理由在相邻的兄弟函数旁反复出现，而不是写在拥有它的那个能力或辅助函数上。
- 段落墙：一段塞进好几条规则与括号补充。
- 强调膨胀：到处都是加粗、大写或「关键的是」。
- implemented Agent Note 里的规格语气：「应当」、迁移计划、验收清单——已交付的记录只描述事实。
- 长期技术设计或决定只留在 Issue / PR 评论，未写回其 Agent Note；本次交付范围、评审或批准流水重复存到本地设计文档。

## 怎么审

审文档或注释时：先定范围，再读这一节与对应工件的家（见根 [`AGENTS.md`](../AGENTS.md) 的「文档与约定」表）；逐处判成**保留、补写、删减、移走**（移走＝搬回拥有它的那一层），先改拥有该事实的原文、再改派生物；报告里说清审了哪些范围、改了什么、故意留下什么、哪些没把握没改。判断不了的不硬改，报告出来。

## 检查

`node scripts/decisions/check.mjs` 负责 Agent Note 的目录、元数据、文件格式与本地链接检查，规则见 [`.agents/notes/README.md`](../.agents/notes/README.md)。代码那一侧的机器门禁是 `cargo fmt --check` 与 `cargo clippy --workspace --all-targets --all-features -- -D warnings`（见根 [`AGENTS.md`](../AGENTS.md) 的「验证」）。其余正文与注释由审阅按本文件把关。
