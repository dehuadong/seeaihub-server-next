# 渠道参数的开启依据是第一方文档，不要求逐个实测

渠道第一方文档（或该渠道公布的机器 Schema）写明支持的参数，**直接声明并开放**。**当前阶段平台不校验取值**（枚举、区间、类型、未知字段都不管），只要求合同的必填项在场——请求里的参数一律放行透传；哪些参数需要把取值管起来，等一份明确的清单后再加（用户 2026-09-20 说明后期统一整理）。不再要求"每个参数先花一次计费调用实测过才开启"（[0002](./0002-native-capability-schema-not-canonical.md) 的"未证实的参数不开启"收窄为只针对**冲突**与**未知字段**）。

**理由**：把"没实测"当成拦截理由，会让能力面长期小于渠道真实能力，而这层差距不产生任何保护——真正需要防的是"平台声明了却发不出去"（静默降级），那由"未声明的参数由平台在受理前处置"和"取值按声明校验"来兜。某个参数**真正需要用到时**再验证它在实际端点上的行为，那时才值得一次计费调用。

**2026-09-20 修订（透传的边界，同日按 [0005](../design/0005-vendor-model-contract-and-offering-mapping.md) 收口）**：请求参数**不是一律透传**——受理时按**该 Vendor Model 的合同**（模型级唯一一份）过滤：合同里没有的字段**直接丢掉，既不报错也不发给上游**（用户 2026-09-20 明确）——**图片字段除外**：`image`/`image_urls`/`mask` 是请求的实质，合同没声明它们时一律 400，不能悄悄退化成文生图；合同里有、但**命中的那条供给承载不了**的字段，则该供给**不合格**（换下一条供给；全都不合格按平台侧故障返回，**不静默丢**）。于是 [0002](./0002-native-capability-schema-not-canonical.md) 那条"未知字段在受理前拒绝"变为"合同外字段在受理前丢弃"。对**合同与承载面都有的**参数，仍然不校验取值、原样发给上游。

**代价**：丢弃是静默的——消费侧多发一个参数不会得到任何提示，若那个参数本该影响结果，效果就悄悄没了。之所以接受，是因为对客合同以候选声明的能力面为准，"这个参数在命中的候选上存不存在"本身随选路变化，逐次报错会把选路结果变成调用方的负担。

**边界（同日登记）**：过滤只比**顶层**属性名——候选声明了 `extra` 这类嵌套面时，它整个留下，里面没逐键声明的键也会原样上行。当前实现里两个 Adapter 都不开放 `extra`，五份发布素材也都没声明它，所以这条**暂不可达**；将来真要开放嵌套面，过滤必须跟着逐键（否则等于在嵌套面里把"未声明也放行"开了个口子）。

**代价**：文档与实际端点不一致时（渠道文档是 OpenAI 兼容面、机器 Schema 却是另一套参数集合），平台可能先声明、后在使用时才发现打不通；这类不一致按渠道事实登记，不靠"一律不声明"回避。
