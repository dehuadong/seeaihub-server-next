# 渠道错误对客一律改写：只用平台错误码，平台侧故障不得算在消费者头上

渠道的状态码、错误码与原文**只留在内部**（Attempt 与管理端），对客只用平台错误码（`platform_unavailable` / `outcome_unknown` / `content_rejected`）。**责任方决定语义**：渠道因**平台的**参数、凭证、权限、额度或限流而拒绝（APIMart 的 `402`/`403`/`429`、以 `500` 承载的参数错误；AIHubMix 的 `401` 与 `403` 各分支）一律是平台侧故障，不返回 4xx；只有渠道明确因**消费者内容**拒绝才是消费者的 4xx；渠道 5xx 同样不透传。**拿不准时按平台侧处理**——渠道说的"账户余额不足"指的是**我们**（AIHubMix 的码就叫 `insufficient_user_quota`），原样返回会让消费者去充值。

平台欠费与用户欠费是两个状态（见 `GLOSSARY.md`）：用户欠费在受理前拒绝、对客可见；平台欠费只在调用渠道时暴露，属**运营事件，必须能被发现**，对客不得表现为"余额不足"。逐条码表见 [`docs/facts/channel-facts.md`](../facts/channel-facts.md) 的 AIHubMix 错误码节与 APIMart 错误码节。

**反悔成本**：改写是**存下来**的，不只是回给调用方那句话——`generation.jobs.error_code` 列的取值范围（白名单 CHECK）与 `public_error_code` 的派生都按这一组取值定，历史行里已经写着这三个码；改成透传渠道错误要迁移这一列与它的 CHECK、把已受理 Job 的对客错误重新定义（而"Job 固定受理时版本"要求旧行不被改写），并同时改对客协议的兼容承诺（今天不返回 4xx）。

**可行的备选是透传渠道错误**（把渠道的状态码与原文直接回给调用方）：落选的理由记在提交 `6866716` 与 `docs/facts/channel-facts.md` 的渠道错误码节——两家渠道都用上游语义描述**平台的**额度与凭证问题（AIHubMix 的 `insufficient_user_quota` 指的是平台账户），原样返回会让消费者以为该去充值，而真正要处理的人（运营）看不到。

**代价**：消费者分不清"渠道挂了""我提交的内容被拒""平台自己出了问题"这三件事的细节，只能知道该不该改内容重试。平台因此**必须自己建发现面**：`GET /api/v1/provider-failures` 与平台故障告警出口（[`0009`](../design/0009-operational-baseline.md)）是这条决定的必要配套，少了它们，改写就等于把渠道事实丢掉而不是收进内部。
