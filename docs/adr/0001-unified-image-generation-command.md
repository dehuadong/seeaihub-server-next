# 文生图、图生图与 mask 编辑共用同一条 Image Generation 命令

三类请求只是同一业务能力的不同输入分支，因此平台只保留一个 `CreateImageGeneration` 命令和一个持久 Generation Job：不拆两套应用服务，也不新增平台 `operation` 字段，分支由原生图片参数派生。拆开会把 Job 表、状态机与结算规则各复制一份；派生分支只用于选 Schema 条件分支、判断 Offering 能否履约、让 Adapter 选择 wire 形态、选计价规则与写审计，它不是客户端字段。

**边界**：若厂商把生成与编辑定义成完全不同的正式模型身份或不兼容合同，就按厂商边界建立不同的 Vendor Model Revision——统一命令不抹平厂商真实的产品差异。

**可行的备选是拆成两条命令**（生成与编辑各一套应用服务、Job 与状态机）或**保留一条命令但加一个平台 `operation` 字段**：前者落选的理由是它把 Job 表、状态机与结算规则各复制一份，两边的口径从此要各自维护（正文已记"拆开会把 Job 表、状态机与结算规则各复制一份"）；后者落选的理由见上面那句——分支由**原生图片参数**派生即可判定（选 Schema 条件分支、判断 Offering 能否履约、让 Adapter 选 wire 形态、选计价规则），多一个客户端可见的字段等于把平台的内部分类写进对客合同。**代价**：分支派生散在受理路径的几个判断点上，不像一个显式字段那样一眼看得全；这是它换来的对客合同稳定所付的价钱。

**反悔成本**：改它要为两个分支各建一套 Job 与 Attempt（或加一列平台 `operation` 并回填），并把既有 Job、Attempt、账本条目与两个对客端点（`/v1/images/generations`、`/v1/images/edits`）的语义重新归属——状态机与结算规则也随之分成两份。
