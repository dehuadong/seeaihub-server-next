# Provider 提交结果不确定时失败关闭，进对账而不自动重提

上游没有公开幂等键、成功调用也不进入可查询任务列表，因此从请求发出到响应落库之间存在"可能已生成、平台却没有结果"的窗口。平台接受这一限制并失败关闭：本地幂等键与数据库唯一约束保证一个 Job 只建立一个 Attempt；Worker 提交前写入 `submitting` 并维护租约，**通用重试器不得重放 Provider POST**；只有明确的连接前失败可以重试，其余（请求可能已发出、超时、中断、崩溃、解析失败）一律进 `reconciliation_required`，**不自动切换 Channel / Offering，不重新生成**。

**可行性备选是把正式计费路径换到 `/ai/v1` 的任务式面**（先被 v4 定为生产路径，v5 放弃）：落选，依据 [`docs/design/0002`](../design/0002-image-generation-tech-design.md) 的修订关系段与 §4——任务对象给得出任务 id 与轮询状态，却**不返回 `usage`、不返回金额**，无法形成可核验的 Metering Evidence，而这条证据是正式结算的门槛（[ADR-0006](./0006-no-settlement-without-metering-evidence.md)）；换成它等于用"能查得到"换掉"算得清"。**代价**：极少数模糊失败无法自动恢复，需要人工对账；换来的是不重复出图、不重复产生上游成本。若实际故障率不可接受，应评估上游的账单 API、幂等能力或其它可核验的计量事实来源，**而不是削弱这条安全规则**。
