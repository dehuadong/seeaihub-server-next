# 同一 Vendor Model 可以有多个 active Offering，选中顺序由已发布优先级决定

同一 Vendor Model 可以由多个 Offering 供应（不同 Provider、Channel 或执行策略）。`publication.runtime_entries` 允许同一型号存在多条 active 记录，各带一个 `routing_priority`，数字小者优先且同一型号内唯一。受理时按优先级升序取**第一个合格候选**，合格是**合取**：该候选的 `restrictions` 允许本次分支与输入图张数，**且**请求满足该候选自己已发布的 Schema。两项都只用受理前已知的事实——不做上游探测，不让 Adapter 参与选路；没有合格候选时在**调用上游之前**失败，不回退到能力更宽但优先级更低的候选。

决定的操作性条款：

- **价格不参与选中**。不按最低价自动排序，也不在运行时比较 Price Plan；发布者若希望优先用更便宜的供给，就把这件事表达为发布时的顺序并记录依据。
- **预授权金额与计价口径是两个量**，不得互相推导：预授权由调用方给出的 `max_cost_microusd` 决定，不由候选价格反算（按张计价时输出张数在受理时不可知）；被选中候选的最小可能费用已超上限时**在受理前拒绝**，而不是留到结算。
- **一次发布携带该型号完整有序的候选集合**，发布即原子替换该型号既有 active 条目，因此候选集永远来自同一个 Revision。
- **一次 Attempt 一旦进入 `submitting`，就禁止改选 Offering 或 Channel**——上游可能已生成并计费，改选等于重复出图与重复计费。
- **受理时必须写一条 append-only 的路由判定记录**（候选列表、被选中者、每个被跳过者的原因）。`active` 是按型号全局可变的事实，只靠 revision id 或模型名事后无法重建"当时考虑过谁、为什么跳过"。
- **限制只能收窄，但不需要"收窄证明"机制**：Profile 声明该 Provider 的实际支持面，Offering 的 `restrictions` 只在其内再收紧——同一事实在两个发布位置的落点，不是从全集推导子集。

**批准依据**：本条的规划评审通过记录在 `#2` 上不可复核，**批准待用户事后确认**（2026-09-20 核对，见工作项 [`#6`](https://github.com/dehuadong/seeaihub-server-next/issues/6)）——本条在实现中生效，但不据此推断已获批准。

**2026-09-20 部分被取代**：本条关于"哪些候选存在、按什么顺序"的部分（一次发布携带完整有序候选集、合格是合取判据、不合格在调用上游前失败、`submitting` 后禁止改选）**继续成立**；"选中顺序完全由发布决定"这一半已由 [0020](./0020-routing-strategy-layer-configured-by-operations.md) 补上——在一批**合格候选**里挑哪一条改由**运营配置的路由策略**决定（未配置时默认 `priority_failover`，行为与今天相同）。其中操作性条款里"`routing_priority` 数字小者优先**且同一型号内唯一**"这半条**已由 [0020](./0020-routing-strategy-layer-configured-by-operations.md) 取代**——**同一档位内可以有多个候选**，档内按 `weight` 分流（"数字小者优先"退为未配置策略时的默认 `priority_failover` 的降级顺序，档内同样是按权重分摊）；"哪些候选存在、按什么顺序"这半条**仍成立**（候选集仍来自同一次发布、顺序仍由发布定），只是"同一型号内唯一"不再是约束。以上原文与结论段不改，仅作标注。

**2026-09-22 修订（预授权/上限条款）**：上文操作性条款第二项"预授权金额与计价口径是两个量，不得互相推导：预授权由调用方给出的 `max_cost_microusd` 决定，不由候选价格反算……被选中候选的最小可能费用已超上限时**在受理前拒绝**"改为——**预授权只是保底额**：按**供给（vendor + offering）维度**的保底表（`floor_amounts`）查得，随修订发布、随 Job 快照冻结、**不编进代码**，**既不由候选价格派生、也不由调用方自报**；**受理闸门是"余额 ≥ 保底额"**（不成立 ⇒ `insufficient_balance`、对客 402，不产生 Job、不扣款）；**结算按实际扣费**，**实际超过保底额时余额可为负（透支发生在结算，不在受理）**——保底额只是结算的参考下限，估小了由透支吸收、估大了释放差额；`GENERATION_MAX_COST_MICROUSD` **退为"连该供给的封顶保底值都查不到时"的兜底保底额**，不再是任何形式的上限，"被选中候选的最小可能费用已超上限时在受理前拒绝"这条规则**已删除**（受理的唯一上限是客户余额）。改这一段的理由：原口径依赖"候选的最小可能费用"这个受理时算不准的量（按 token 计费的渠道受理时不知道真实用量），既算不准又会把正常请求拒掉；把预授权降为"保底 + 允许透支"后，估不准由结算吸收，而**余额不足**才是硬拒绝。
