# 受理路径的容量测量记录

- **用途**：为「先饱和的是哪个资源」提供可判定的观测。设计与要量的数由 [`.agents/notes/proposed/platform/2026-10-09-admission-path-capacity-measurement.md`](../../.agents/notes/proposed/platform/2026-10-09-admission-path-capacity-measurement.md) 拥有，本文只记命令、观测与结论。
- **读者**：要用这组数决定缓存范围的人。
- **前置**：本机 PostgreSQL 与 `HTTP_CONTRACT_DATABASE_URL`；假上游由测试夹具提供，无真实计费调用、无外网。
- **记录方式**：结论写在本文，工作项只链接它。

## 结论

**已判定：先饱和的不是连接池。** 三条正面证据：

1. **池 10 与池 64 的吞吐没有一致差异**。两个方向都有、幅度在 10% 量级，落在同一档重复跑的散布里（同一档约 ±10%）。池 10 时后端数峰值顶在 11、池 64 时到 52——**池确实被用满，但用满不是限住吞吐的原因**。
2. **账户行锁排除**。同一档把账户数从 1 提到 8（密钥轮流用），吞吐没有一致提升：并发 8 是 44.12 → 46.61、并发 16 是 44.63 → 47.86、并发 32 是 40.60 → 40.08。
3. **整机 CPU 排除**。全部 25 档的整机忙碌率在 1.9%–15.1% 之间。

**未判定：Z 到底是什么。** 缺的数见「缺的数」——夹具只有一条渠道，扫不出渠道这一轴。按验收条件 4，这里不给替代结论。

两条观察支持「排在一条串行资源后面」，但它们**不构成对 Z 的判定**：延迟随并发线性上升而吞吐持平（0 毫秒档并发 1 时一次请求约 48 毫秒，并发 8 起吞吐不再上升而平均延迟从 159 毫秒涨到 613 毫秒）；每请求的连接占用时间在并发 1 时是 25 毫秒、并发 32 时升到 42–60 毫秒，占用随排队一起涨。

吞吐量级：**0 毫秒档封顶在约 40–47 请求/秒**（并发 8–16）；**200 毫秒档到并发 32 仍在上升**（4.03 → 38.26 请求/秒），没有封顶。

### 每请求的 SQL 工作量

`pg_stat_statements` 在本机没加载，语句级计数缺席。可读的是**表级扫描计数**（`pg_stat_user_tables` 的 `seq_scan + idx_scan`），按每请求摊开：

| 表 | 每请求访问次数 |
| --- | --- |
| `generation.jobs` | 10–15 |
| `ledger.accounts` | 5–7 |
| `generation.attempts` | 3–5 |
| `supply.offerings` | 2.4–3.3 |
| `publication.runtime_revisions` | 2.4–3.3 |
| `supply.channels` | 2.4–3.3 |

合计约 30 次表访问、8–13 次已提交事务。缓存候选里最贵的那次读（候选与定价的六表 JOIN）就落在 `offerings`、`runtime_revisions`、`channels`、`vendor_models` 那几行上。

### 非生成流量

同一档（0 毫秒延迟、池 10、账户 1、并发 8）各跑一次，只差后台压不压目录读：

| 后台读路数 | 生成吞吐 | 生成平均延迟 | 每请求连接占用 | 后台完成读次数 | 总已提交事务 | 后端峰值 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 45.50/s | 155.4ms | 21.2ms | 0 | 1212 | 12 |
| 8 | 40.05/s | 165.1ms | 21.7ms | 993（约 331 次/秒） | 1840 | 12 |

压 8 路 `GET /v1/models`（约 330 次/秒）时：生成延迟升 6%，生成吞吐低约 12%——**比本组自报的 ±10% 散布略大**，所以只能说影响有限，不能说完全不挤占。同一档里每请求的连接占用与后端峰值都没变（21.2 → 21.7 毫秒、12 → 12），总事务数升约 52%，所以挤占不发生在连接占用上。

## 方法说明

- **用例**：`harness::cases_capacity_measurement::the_admission_path_saturation_sweep`
- **命令**：`HTTP_CONTRACT_DATABASE_URL=<本机 .env 的 DATABASE_URL> cargo test -p seeai-api --test http_contract -- --ignored --nocapture --test-threads=1 cases_capacity_measurement`
- **构建**：`cargo test` 测试 profile（未优化 + debuginfo）
- **机器**：11th Gen Intel Core i7-11700 @ 2.50GHz（16 逻辑核）、约 15.5GiB 内存、WSL2 x86_64
- **负载**：每档 120 次**尝试**，本组全部成功（`failures=none`）。`GENERATION_EXECUTION_SLOTS` 与 `GENERATION_MAX_CHANNEL_IN_FLIGHT` 在测量里抬开（内存预算 16 GiB、渠道名额 256），否则量到的是那两道闸门——所以**执行名额占用这一项没有数**。每档都用一个**大余额**账户，避免 402 混进容量结论。
- **口径**：吞吐与延迟只统计成功请求；`后端` 报「空闲基线 / 峰值」，读的是 `pg_stat_activity` 里该一次性库的后端数，含夹具自己的池；`连接占用` 是「不空闲后端数 × 50 毫秒采样间隔 ÷ 请求数」，是个近似量；`事务` 是该库这一档的 `pg_stat_database.xact_commit` 增量；表访问按同一档的 `pg_stat_user_tables` 增量摊到 120 次请求上；`CPU` 是整机忙碌率，按 `/proc/stat` 前后两次快照算。缓存层在本组测量里**关闭**（夹具不给 `REDIS_URL`）。
- **散布**：同一档重复跑之间，吞吐的散布约 ±10%（0 毫秒、池 10、并发 8 四次跑出 47.68、47.36、44.91、45.50）。下面的表来自**一次**完整跑，所以单格差值不当作结论。整轮约 185 秒。

## 设计里要的五个数：交付与缺口

| 要的数 | 状态 | 说明 |
| --- | --- | --- |
| 每请求 SQL 条数与语句分类 | **部分** | 有每请求约 30 次**表级**访问（含分类）与 8–13 次已提交事务。**没有语句级**计数：`pg_stat_statements` 在本机未加载，当前角色也没有权限装它。 |
| 每请求的连接占用时间与池等待 | **部分** | 有每请求的连接占用时间（后端秒 ÷ 请求数，见各表的「连接占用」列）。**池等待时间与等待次数没有**：池在 API 进程内，夹具只能从 PostgreSQL 一侧看，要进程内插桩才量得到。 |
| PostgreSQL 每语句耗时与调用次数 | **未交付** | 同上：`pg_stat_statements` 缺席。 |
| 吞吐—并发拐点及拐点处各资源的值 | **部分** | 0 毫秒档的拐点在并发 8–16，200 毫秒档到 32 仍在上升。资源值有后端数峰值、连接占用与整机 CPU；**执行名额占用没有**（测量里被抬开）。 |
| 非生成流量能否与生成请求互相排队 | **交付** | 见「非生成流量」。 |

## 与设计矩阵的偏差

设计里写的是「上游延迟 0／200 毫秒／2 秒 × 并发 1–64」。实际跑的是 0／200 毫秒 × 并发 1–32，另加连接池、账户数与后台读三轴。两处收窄的理由：

- **去掉 2 秒**：秒级延迟下上游占绝对大头，各档都落在执行名额之内，扫不出拐点。
- **并发上限从 64 降到 32**：内存预算要装得下那么多并发执行，同时把整轮压在 CI 的 30 分钟预算里。

## 缺的数

- **渠道数这一轴没有扫**。夹具只有一条渠道，所以「先饱和的是哪个资源」判不出来。要判定它，需要一份**两条候选分走两个渠道**的夹具：如果吞吐随渠道数成比例上升，串行点就在渠道上；如果不动，串行点在同一条渠道之外的共享资源上。
- **池等待时间与等待次数**：池在 API 进程内，要插桩。
- **执行名额占用**：测量把这道闸门抬开了，所以它的值没有数。
- **语句级计数与每语句耗时**：`pg_stat_statements` 本机装不了。
- **秒级上游延迟**（同上）。
- **多副本没有测**。多个 API 进程共享一台 PostgreSQL 时渠道锁与池的竞争，本组测量覆盖不到。
