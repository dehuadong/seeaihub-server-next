# 受理路径的容量测量记录

- **用途**：为「先饱和的是哪个资源」提供可判定的观测。设计与要量的数由 [`.agents/notes/proposed/platform/2026-10-09-admission-path-capacity-measurement.md`](../../.agents/notes/proposed/platform/2026-10-09-admission-path-capacity-measurement.md) 拥有，本文只记命令、观测与结论。
- **读者**：要用这组数决定缓存范围的人。
- **前置**：本机 PostgreSQL 与 `HTTP_CONTRACT_DATABASE_URL`；假上游由测试夹具提供，无真实计费调用、无外网。
- **记录方式**：结论写在本文，工作项只链接它。

## 结论

**在并发 8–32、上游延迟 0–200 毫秒下，单进程吞吐封顶在约 41–49 请求/秒；先饱和的既不是连接池，也不是 PostgreSQL 后端数或整机 CPU。**

三条排除：

1. **连接池不是**。把 `DATABASE_MAX_CONNECTIONS` 从 10 提到 64，吞吐的差异**两个方向都有**、幅度在 10% 量级，落在同一档重复跑的散布里，没有一致提升。池 10 时后端数峰值顶在 11，池 64 时同一档到 51，吞吐一样——池**确实被用满**，但用满不是限住吞吐的原因。
2. **账户行锁不是**。同一档下把账户数从 1 提到 8（密钥轮流用），吞吐没有提升（并发 8：43.07 → 48.13；并发 16：48.89 → 49.58；并发 32：44.07 → 43.23）。
3. **整机 CPU 不是**。全部 25 档的整机忙碌率在 1.6%–15.1% 之间。

剩下的候选是**受理事务里按渠道串行化的那一段**：`admit` 先取 `pg_advisory_xact_lock(hashtextextended('channel:<channel_id>', 0))`，直到提交才释放，同一条渠道上的全部受理因此排队。夹具只有一条渠道，所以这是**排除法指向的结论，不是正面确认**。见「缺的数」。

延迟随并发线性上升、吞吐持平，正是排在一条串行资源后面的形状：并发 1 时一次请求约 43 毫秒（1 ÷ 0.043 ≈ 23 请求/秒），并发 8 起吞吐不再上升而平均延迟从 148 毫秒涨到 563 毫秒。

### 每请求的 SQL 工作量

`pg_stat_statements` 在本机没加载，语句级计数缺席。可读的是**表级扫描计数**（`pg_stat_user_tables` 的 `seq_scan + idx_scan`），按每请求摊开：

| 表 | 每请求访问次数 |
| --- | --- |
| `generation.jobs` | 11–16 |
| `ledger.accounts` | 5–7 |
| `generation.attempts` | 3.5–4.7 |
| `supply.offerings` | 2.6–3.6 |
| `publication.runtime_revisions` | 2.6–3.6 |
| `supply.channels` | 2.5–3.6 |

合计约 30 次表访问、9–13 次已提交事务。缓存候选里最贵的那次读（候选与定价的六表 JOIN）就落在 `offerings`、`runtime_revisions`、`channels`、`vendor_models` 那几行上。

### 非生成流量

**共用同一个池，读那一侧基本不挤占生成。** 同一档（0 毫秒延迟、池 10、账户 1、并发 8）各跑一次，只差后台压不压目录读：

| 后台读路数 | 生成吞吐 | 生成平均延迟 | 后台完成读次数 | 总已提交事务 | 后端峰值 |
| --- | --- | --- | --- | --- | --- |
| 0 | 48.68/s | 145.8ms | 0 | 1305 | 11 |
| 8 | 42.15/s | 159.5ms | 1007（约 353 次/秒） | 1934 | 12 |

压 8 路 `GET /v1/models`（约 350 次/秒）时：生成延迟几乎不变（146 → 160 毫秒），池的后端峰值不变，总事务数上升约 48%，生成吞吐落在 42–43/秒——比同一档不压读时的 45–49/秒低约 6%–13%，仍在重复跑的散布量级内（见「方法说明」）。也就是说两类流量在池上**不互相排队**：每个请求占连接的时间都很短。

## 方法说明

- **用例**：`harness::cases_capacity_measurement::the_admission_path_saturation_sweep`
- **命令**：`HTTP_CONTRACT_DATABASE_URL=<本机 .env 的 DATABASE_URL> cargo test -p seeai-api --test http_contract -- --ignored --nocapture --test-threads=1 cases_capacity_measurement`
- **构建**：`cargo test` 测试 profile（未优化 + debuginfo）
- **机器**：11th Gen Intel Core i7-11700 @ 2.50GHz（16 逻辑核）、约 15.5GiB 内存、WSL2 x86_64
- **负载**：每档 120 次**尝试**，本组全部成功（`failures=none`）。`GENERATION_EXECUTION_SLOTS` 与 `GENERATION_MAX_CHANNEL_IN_FLIGHT` 在测量里抬开（内存预算 16 GiB、渠道名额 256），否则量到的是那两道闸门。每档都用一个**大余额**账户，避免 402 混进容量结论。
- **口径**：吞吐与延迟只统计成功请求；`后端` 报「空闲基线 / 峰值」，读的是 `pg_stat_activity` 里该一次性库的后端数，含夹具自己的池；`事务` 是该库这一档的 `pg_stat_database.xact_commit` 增量；表访问按同一档的 `pg_stat_user_tables` 增量摊到 120 次请求上；`CPU` 是整机忙碌率，按 `/proc/stat` 前后两次快照算。缓存层在本组测量里**关闭**（夹具不给 `REDIS_URL`）。
- **散布**：同一档重复跑之间，吞吐的散布约 ±10%（例如 0 毫秒、池 10、并发 8 四次分别跑出 47.68、47.36、44.91、48.68）。所以下面只报量级与方向，不把单次差值当结论。整轮约 180 秒。

## 设计里要的五个数：交付与缺口

| 要的数 | 状态 | 说明 |
| --- | --- | --- |
| 每请求 SQL 条数与语句分类 | **部分** | 有每请求约 30 次表访问（含分类，见上表）与 9–13 次已提交事务。**没有语句级**计数：`pg_stat_statements` 在本机未加载，本机角色也没有权限装它。 |
| 每请求的连接占用时间与池等待 | **未交付** | 池在 API 进程里，夹具只能从 PostgreSQL 一侧看后端数。占用时间与等待次数要进程内插桩，本轮没有插桩（因此也没有插桩开销）。 |
| PostgreSQL 每语句耗时与调用次数 | **未交付** | 同上：`pg_stat_statements` 缺席。 |
| 吞吐—并发拐点及拐点处各资源的值 | **交付** | 0 毫秒的拐点在并发 8–16 之间，200 毫秒的拐点在并发 32。资源值有后端数峰值与整机 CPU；连接池另有一轴（10 对 64）。 |
| 非生成流量能否与生成请求互相排队 | **交付** | 见「非生成流量」。 |

## 与设计矩阵的偏差

设计里写的是「上游延迟 0／200 毫秒／2 秒 × 并发 1–64」。实际跑的是 0／200 毫秒 × 并发 1–32，另加连接池、账户数与后台读三轴。两处收窄的理由：

- **去掉 2 秒**：秒级延迟下上游占绝对大头，各档都落在执行名额之内，扫不出拐点。
- **并发上限从 64 降到 32**：内存预算要装得下那么多并发执行，同时把整轮压在 CI 的 30 分钟预算里。

## 缺的数

- **渠道数这一轴没有扫**。夹具只有一条渠道，所以「渠道咨询锁是那条串行资源」是排除法的结论，没有正面证据。要确认它，需要一份**两条候选分走两个渠道**的夹具：如果吞吐随渠道数成比例上升，串行点就是渠道；如果不动，串行点在同一条渠道之外的共享资源上。
- **秒级上游延迟没有进这一轮**（同上）。
- **多副本没有测**。多个 API 进程共享一台 PostgreSQL 时渠道锁与池的竞争，本组测量覆盖不到。
- **语句级与连接级的数缺席**（见上一节）。
