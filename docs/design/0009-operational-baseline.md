# 运维底线与运行面

本文承载上线运行所需的**运维面机制**：健康检查、worker 终止信号收尾、并发与配额、API Key 吊销、账目可见与平台故障告警出口。产品范围与验收不在这里；数值（阈值、窗口、次数、时限、上限）一律是配置，取值由运维与运营定。

## 1. 健康检查

**探依赖，不探"能不能干活"**：进程自己的健康由它依赖的**事实源**决定——数据库不可用即不健康。缓存、渠道可用性都不参与判定。

**缓存不可用只算降级。** 缓存是加速层，不可用时系统按"没有缓存"继续服务（直查数据库那条路径本来就在），把它算作不健康会让编排系统重启一个本来能服务的实例。渠道侧失败是**单次请求**的结果（进对账或对客报错），不是进程健康问题。

**响应形状**：健康时 `200` 加 `{"status":"ok"}`；数据库不可用时 `503` 加 `{"status":"unhealthy","database":"unreachable"}`——状态码与字段名是编排系统的判据，不随日志格式变化。探活本身带超时（配置项）：依赖卡住时健康检查要及时给出"不健康"，不能自己挂在依赖上。

**探活是只读且幂等的**：不写库、不改任何状态，可以被编排系统按很短的间隔反复调用。它不承载就绪语义之外的东西——不查渠道、不查队列长度、不报业务指标。

**worker 没有 HTTP 面**：它的存活由编排系统看进程，它自己的进度由租约心跳体现；不为它新增健康检查端点。

## 2. worker 收到终止信号

**排空，不硬退。** 收到终止信号后**不再领新的一轮**，把手上那一轮跑完再退出：在飞的上游调用、计量落库与结算都要收干净。硬退会把在飞调用连同 future 一起丢掉，Job 留在"提交中"直到租约过期才被回收——消费者要多等一个租约周期，运营侧还会看到一批本该正常的对账案例。

**时限由部署给，进程不自设。** 编排系统在终止信号之后给一个宽限期，超时它发强杀；本进程不为排空另设超时，也不因为"排空太久"改写 Job 的处置。宽限期短于一次上游调用的最坏耗时，是这个部署配置的问题，不是进程逻辑的问题。

**强杀之后仍不丢事实。** 被强杀时未完成的 Job 由既有的**过期租约回收**兜住；已提交给上游但状态不确定的，按既有口径进对账，**不自动重提**——重试是另一条线的能力，不在这里顺手加。

**两种信号走同一条路径**：容器里是 `SIGTERM`，本地开发是 Ctrl+C（`SIGINT`），都触发同一段排空逻辑。

**排空与终止不是一个量。** 进程内的排空开关（`watch` 通道）与终止信号都归"停机输入"，主循环只在**领下一轮之前**看它们：两者都不打断手上那一轮，区别只在收到终止信号就**立即**不再领、而排空开关是为将来的"排水"接口留的入口——今天只有测试会置位它，还没有对外端点。主循环把停机输入当参数收，因此"在飞未跑完就不许返回"这条合同可以在测试里确定地验（真信号没法在进程内精确投递）。

## 3. 并发与配额

**只有并发这一个维度**：**每账户在每个网关模型上的在飞 Job 数**（保护渠道），加上渠道的全局未决上限与本机读取、执行容量。平台**不设按 API Key 的请求速率限制**："每分钟最多多少次"不是这里的维度，也没有替代的速率配额。这些量都与金额无关：受理的金额判定只有"已结算余额 − 持有中 ≥ 保底额"那一道（[`0002`](../specs/0002-account-funds-and-reservations.md) §5）。

**超限的对客语义**：`429` 加对客可辨的错误码（并发 `too_many_in_flight`、上传并发 `upload_busy`），并给 `Retry-After`（秒）——什么时候能再来是消费者要的答案，不给它就只能盲目重试。`rate_limit_exceeded` 只剩公开鉴权端点的失败尝试限制（防撞库）在用。

**容量判定不依赖缓存**：并发计数落在 `generation.jobs`（与受理同事务、账户行锁下判定），渠道与上传容量各有自己的账；缓存降级不会让容量闸门失灵，也不会因为加速层挂了就把请求拒掉。公开鉴权端点的失败尝试计数仍落在缓存里，且缓存不可用时放行。

**并发名额按模型给、用已有的在飞计数**：同一账户在**同一个网关模型**上的在飞 Job 数在受理路径上判定，与既有的“在飞上限”同一处，不新增第二套计数。名额由运营在**发布或编辑**时按模型给（列必填；发布命令没给时新建的模型按平台固定值 1——平台规则，不是配置来源），判定按「账户 × 模型」——不再有按账户合计的在飞上限。

## 4. 吊销 API Key

**只有客户能吊销自己的密钥**：`DELETE /v1/customer/api-keys/{key_id}` 由客户会话按自己的账户执行；管理端没有这条路径（运营判断不了客户是否在用，也拿不到要吊销的标识，见 Spec `0001` M5／V-D16）。

**写吊销时间，不删行**：该接口写 `revoked_at`，行留着——密钥的创建与吊销是历史事实，审计与排障都要它；重复吊销是幂等的（已吊销再调仍是成功）。

**吊销即刻生效，因此密钥解析不进缓存。** 认证路径每次按密钥标识读数据库判定吊销状态。把"这个密钥还有效吗"缓存起来，等于让吊销在缓存 TTL 内不生效，而吊销正是"立刻停止使用"的动作，它的语义不允许有窗口。若将来要为解析加速，缓存里只能放"密钥标识 → 账户"的映射，**吊销判定仍然每次读库**——加速不能改变判据。

## 5. 账目可见

**两个面，两种读者**：对客 `GET /v1/account` 提供自己的三个金额字段，客户控制台只显示一个「余额」（客户现在能用的钱）；管理员账户读可查看已结算余额、持有中与可用额，`GET /api/v1/accounts/{account_id}/entries` 按账户看真实收支流水。对客面只给调用者自己的账户，管理员面要管理员凭证。

**客户页面的余额是客户现在能用的钱**：充值增加、实际扣费减少；请求受理时按占住的额度减少，结算后按实际扣费多退少补。持有中与已结算余额只用于后台占用、受理判定与对账，不在客户页面分别展示；账户金额语义见[账户资金 Spec](../specs/0002-account-funds-and-reservations.md) §1、§4。

**余额的权威在数据库。** 两个读接口都以库为准；缓存只作加速，**不得作为答案来源**——缓存的值可能滞后、也可能刚被对账覆盖写回，而这两个接口的用途正是查看与核对，拿被怀疑的一方作证没有意义。

**流水是实际收支的可读视图**：按时间倒序、`since` 增量拉、`limit` 分页；每条带 `kind`（入账 / 扣费 / 调整 / 成本）与有符号金额（人民币微单位）。预授权与释放只留在 Hold 和 Job，不出现在资金流水。账户当前额与流水在同一数据库事务更新，账实核查独立运行。

**读接口只读**：不改状态、不写审计——读不是变更。

## 6. 平台故障告警出口

**出口是配置项**：`PROVIDER_ALERT_WEBHOOK`（POST JSON）；没配就不告警，不内置默认地址。

**触发条件是平台侧事件**：平台欠费或凭证类失败、对账案例新增、某候选连续失败 N 次（N 是配置）。消费者自己的失败不在这里——那是请求结果，不是运维事件。

**载荷给定位所需的最小集**：job、渠道、失败类别、时间。**不带凭证、不带提示词与图片**——告警外发到仓库之外，对客内容不出门。

**发送失败不阻塞主流程**：告警是旁路。发送失败只记日志与计数，不改 Job 的处置、不影响结算与对客结果；超时与重试有界（配置）。告警平台、聚合与静默期是接入方的事，这里不做。
