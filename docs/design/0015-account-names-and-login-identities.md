# 账户名称与登录开通设计

本设计承接[账户名称与客户邮箱登录 Spec v3](../specs/0003-account-names-and-login-identities.md) §2–§6（该修订已接受，生效 v3；v2 已被 v3 取代）。它补充[身份设计](0010-identity-and-consoles.md)及[控制台信息架构](0011-console-information-architecture.md) §4.3–4.4 的账户资料与开户行为，既有认证、金额、详情导航、密钥及口令重置机制继续有效。

## 1. 数据归属与模块职责

名称保存在 `ledger.accounts.name`，非空，不在 `identity.customers` 中保存副本。账户列表、账户摘要、管理员客户视图与客户账户读都从同一账户行投影名称；客户视图通过现有 `account_id` 关联读，不新增业务客户实体。

**自动生成只有一处实现**：application 层的纯函数按下表生成，由三个真正新建账户的路径在写入前调用（管理员建账户、管理员新建并开通、客户自助注册）；绑定已有账户不新建也不改名，不调用它。API、Web 与持久化都不各自拼名称。

名称含账户 id 片段，所以**账户 id 必须在生成之前就定下来**：把铸造账户 id 的责任统一上提到 application 层的用例（`create_account`、`create_customer`、`open_customer_account` 的新建分支），repository 改为**接收** `AccountId` 并只负责写入；现在这三处的 id 分别由 API 层与 persistence 内部 `Uuid::new_v4()` 铸造，本次一并收拢到用例，否则生成函数拿不到 id。

| 输入 | 首选生成结果 | 例 |
| --- | --- | --- |
| 有登录邮箱、本地部分可用 | `<邮箱本地部分>_<账户 id 前 4 位，小写十六进制>` | `zhangsan_3f9a` |
| 无登录邮箱，或本地部分为空／含控制字符 | `账户_<账户 id 前 8 位>` | `账户_3f9a2b1c` |

名称**唯一**（Spec N1），所以函数给出的不是一个名称而是一串**候选**（`generated_account_name_attempts`），由调用方依次尝试到第一个未被占用的：邮箱形式把 id 片段依次加长为 4、6、8、12、16 位；`账户_` 形式从 8 位起步，依次加长为 8、12、16 位，并始终排在邮箱形式之后作为兜底（邮箱形式全部撞名、或本来就没有邮箱时用它）。候选用尽（实际不可能）时创建失败并报冲突。候选生成是纯函数，占用判定在写入侧（见 §2.2）。

邮箱本地部分取 `@` 之前的部分并去掉首尾空白；邮箱在此路径上已按既有规则小写化，函数不再改写大小写。每个候选都保证满足 N2：本地部分超长时截到「100 减去后缀长度」个字符再加后缀（邮箱校验目前**不限制长度**，所以这条必须自己兜）；含 N2 拒绝的字符（`Cc`、`Cf`；`U+200D`／`U+200C` 这两个例外不算）时整体回退到无邮箱形式（邮箱校验也不挡这些字符）；最终结果再过一次与 N2 相同的校验。字符判定用既有 Unicode 分类，不手写区间表。

名称是账户资料，不触发资金版本递增或 Redis 余额快照更新，也不写账户的 `updated_at`——与既有的标签更新一致（该列的既有语义与暴露方式不变，本次不动）。名称的修改时刻由审计记录承载。名称读直接走 PostgreSQL，不新建缓存。

平台账户（`ledger.accounts.kind = 'platform'`，迁移 `0019` 种下的那一行）不是“服务对象”，**不参与自动生成**：迁移直接给它写「平台账户」。它是否出现在账户列表里沿用现状，本项不改。

## 2. 数据库与事务

### 2.1 迁移

两条顺序迁移：`0028` 添加 `name text`——先把已有行回填为 `账户_<账户 id 前 8 位>`（`kind = 'platform'` 的那一行回填为「平台账户」），再置 `NOT NULL`，并加 `CHECK (char_length(name) BETWEEN 1 AND 100)`；`0029` 让名称唯一——唯一性是**大小写不敏感**的，索引用 `CREATE UNIQUE INDEX accounts_name_key ON ledger.accounts (lower(name))` 表达（`lower(text)` 是 immutable，可以进索引表达式）。建索引前先把已经重名（含只差大小写）的行拆开：重复组里保留最早那一行，其余改成 `left(原名称, 67) || '_' || 该行完整账户 id`（32 位十六进制，长度恰好不超过 100，后缀因 id 唯一而唯一）；改名整体放在循环里跑到“一轮无改动”为止——单条 `UPDATE` 不是不动点（改名结果可能正好撞上另一行已有的名字），循环退出后仍有重名就让建索引失败中止迁移，绝不悄悄留下重名。两步都不读取邮箱或标签生成名称、不修改已有历史迁移。应用层负责 Unicode 首尾空白与控制字符规则（数据库只保底长度与非空）。开发库允许直接重置后空表迁移，回填与去重是给非空开发库兜底，不是产品行为。

名称字面子串搜索先使用参数化查询，保持现有受限列表。不新增扩展或搜索索引；包含式搜索不能指望普通 B-tree 索引加速。若真实数据量与测量表明需要性能优化，再评估 trigram 等索引，不把它作为本次依赖。

### 2.2 管理员创建账户

扩展现有 `create_account` 用例与 repository 入参：名称缺省时按 §1 的候选序列**循环尝试**（撞名就换下一个候选，只有候选全部撞名才失败），名称、可选标签与初始充值进入已有创建事务。调用方显式给出的名称只有一个候选——撞名即冲突，不做改名或加后缀。该事务写账户行、非零初始充值分录和审计，一起提交；成功后仍按原机制更新余额加速层。Web 不再在创建成功后另发写标签请求，因此不再有“账户已创建但标签没写入”的中间状态。已有独立标签编辑接口继续有效。

API 解码必须区分**省略**与**显式 `null`**：省略走生成，显式 `null`、空串或纯空白按 N2 返回参数错误；不能把两者都折叠成 `Option<String>::None`。旧请求缺少名称或标签时仍然合法（名称走生成），这不改变“接口调用方可以不给名称”的事实。

名称更新通过独立 `PUT .../name` 用例，仅更新资料和审计，同一事务完成；账户不存在返回 NotFound。并发改名沿用普通资料写入的后写覆盖，不新增版本协商协议。

### 2.3 新建账户或绑定邮箱身份

扩展 `open_customer_account` 的可选新账户名称。校验 `account_id` 和 `account_name` 不可同时提供，在取哈希或数据库写入前拒绝错误组合。新建路径：给了名称就用规范化后的值（撞名即冲突），没给就按该登录邮箱的候选序列循环尝试；名称与账户、身份在同一事务里成立，冲突时整个事务回滚、不留身份。旧请求省略名称继续创建账户（名称由生成补齐）。

绑定路径不改写账户任何资料，也不接受名称。保留 `identity.customers` 对 `lower(email)`、`account_id` 的唯一索引；预先查询用于明确提示，最终唯一约束处理竞态。**名称的唯一索引同属这一类**：账户名被别的账户占用时同样映射为 Application Conflict（`409`），而不是普通数据库错误，整个事务回滚。三条唯一约束（邮箱、账户绑定、名称）都按同一方式兜底：写入前查一次给出说得清的答复，约束负责竞态。

开户响应和客户列表／按邮箱／按 id 读取统一读取账户名称投影；不要仅给开户响应拼输入名称，否则已有账户路径和后续改名会不一致。

### 2.4 客户自助注册与客户改名

客户自助注册沿用 `create_customer`，在创建账户与身份前按 §1 用该邮箱的候选序列循环尝试（短片段被别人占了就加长再试），注册请求不新增任何字段，客户端不需要知道名称的存在，也不该因为“生成的短名字恰好被占用”而失败。

客户改自己的账户名称走新用例，只接受**会话已确定**的账户 id（不接受请求体里的 id，也没有“改别人账户”的入口），名称规则与 N2 相同（不能清空），同一事务写资料与审计；审计沿用既有约定：管理员那条 actor 是 `admin-api`、客户那条是 `customer-self-service`，`action` 分别为 `account.name_set`，`subject_type` 为 `account`，payload 记旧值与新值（与 `account.tag_set` 的形状一致）。账户不存在按会话已确定的前提不可能发生，参数非法返回参数错误，**改成别的账户已用的名称（含只差大小写）返回冲突**且不改动任何资料；改成自己原来的名称（仅大小写不同）不算冲突。并发改名同样后写覆盖。

## 3. 查询和接口

`AccountSummary` 增加 `name: String`（非空），管理 `CustomerView` 增加 `account_name: String`（非空）；Web 对应类型为 `string`。既有各字段保留；对客登录／会话响应不加入名称。所有返回管理 `CustomerView` 的路径都应采用同一关联读，以免查找与详情丢字段。

账户查询增加独立名称条件，保留现有邮箱大小写不敏感精确匹配、标签精确匹配和多条件 AND 语义。对规范化后的名称查询做 PostgreSQL 大小写不敏感子串匹配；SQL pattern 中先转义反斜线、`%` 和 `_`，明确 ESCAPE 字符，再绑定参数。不能直接拼 SQL，不能把用户输入当模式。顺序继续为 `created_at DESC, id DESC`，limit 上限继续沿用现有实现。

对客账户读**新开一个响应类型**（例如 `CustomerAccountResponse { name, balance_microusd, held_microusd, available_microusd, updated_at }`），从同一个 `BalanceChange` 映射，只挂在 `GET /v1/customer/account` 上；API Key 面的 `GET /v1/account` 继续用现有 `OwnAccountResponse`，形状一个字段都不变——两者现在共用同一个响应类型，直接加字段会把 API Key 面也改掉（违反 Spec `0003` §5 与 Spec `0001` §6）。

名称筛选与唯一性是两件事：筛选是子串匹配（可命中多个不同名账户），唯一性约束只挡完全同名（大小写不敏感）。HTTP 增量和状态码以 Spec §5 为准，创建账户保留现有响应与成功状态，不顺便调整为另一种协议；撞名统一用既有的 `409 Conflict`（与邮箱冲突同一形状），不新造错误码。新增写接口（管理员改名、客户改名）加入各自的认证端点集合与认证验证矩阵。名称创建／修改审计记录 account id、actor（管理员或客户）、规范化值、旧新值，不增加密码或令牌资料。操作者归因继续沿用现有审计机制，本变更不扩展管理员角色或改造整套审计。

## 4. Web 交互

账户创建表单的名称是可选输入，提示“留空将自动生成，如 `zhangsan_3f9a`；也可现在填写，之后随时修改”；标签文案为“路由标签”，解释仅用于配置标签路由；初始充值沿用原金额校验。创建一次提交名称、标签与金额，请求处理中禁用确认并阻止重复提交；成功按既有逻辑进入新账户详情，详情显示最终名称（含生成的那一种）。确定的校验或事务失败保留表单并显示可重试错误；请求发出后网络中断、超时或成功响应无法解析属于结果未知，提示“创建结果暂未确认，请先按账户名称查找确认”，提供进入名称筛选的入口，不自动重试或宣称可直接重新创建。名称编辑放在账户资料区域，和路由标签分开提交，保存后重取摘要。

客户登录页保留现有 hash 地址与 customer id。开户表单用两个明确模式：新建模式显示登录邮箱与可选名称；已有模式显示完整账户 id 输入和只读预览，不显示名称输入。切换模式清除不适用字段，最终请求只包含当前模式的资料。

预览用 account summary 接口，提交守卫同时核对当前输入 id、成功预览 id 和未绑定状态。切换 id 清旧数据；以取消请求或请求序号忽略迟到响应；关闭表单清所有预览。最终写入仍依赖服务端约束：撞名（`name_taken`）时留在表单上提示“这个名称已被占用，请换一个”，邮箱或账户绑定冲突（`conflict`）提示对应的原因，两者都不自动创建另一账户。

客户控制台的“账户设置”页增加账户名称字段：普通单行文本输入，说明文案固定为“账户名称用于识别与账单，可随时修改”；保存成功后显示新值并给出成功反馈，失败保留原值并可重试，保存过程中禁止重复提交；不能清空（提交空值由前端与服务端各拦一次）。页面只呈现名称本身，不解释自动生成规则、不提账户 id 片段或邮箱拼接，也不区分“系统生成的”与“自己改的”。名称只以文本渲染，不解析 HTML。

两处列表与详情名称按文本显示。账户列表增加独立名称筛选，将它加入现有会话级筛选恢复状态；URL 不增加名称或邮箱。客户登录列表与详情直接展示 `CustomerView` 的 `account_name`，不对每行另发摘要请求，避免逐行查询。保留账户 id、登录邮箱和路由标签，便于在名称之外确认对象（名称唯一，但仍有形近与语义相近的名称）。

## 5. 发布与恢复

本仓库没有独立的迁库步骤：迁移经 `sqlx::migrate!` 编译进二进制，API 与 Worker 都在启动路径上执行，所以“先迁移再换代码”是同一件产物的两个动作。真正要写清的是**混合版本**：名称列是 `NOT NULL` 且无默认值，**任何旧二进制**（回退后的实例、或与新库并存的旧实例）执行 `INSERT INTO ledger.accounts` 都会失败，建账户与客户自助注册因此中断。因此：迁移只能与支持名称的 API 一起上；**回退到旧 API 需要先跑一条补默认值的迁移，或按开发阶段直接重置开发库**，不能假设“列还在就能回退”。Web 不能先于新 API 发布，因为它要发送并展示 `name`。

名称迁移不执行数据重建，已存在开发库行由迁移回填占位名（平台账户回填「平台账户」），之后由运营或客户改成真名。唯一索引是 `0029` 的后半段：它在去重之后建立，回退 Web 或 API 都不会自动消失——回退到**不支持名称唯一**的旧 API 时，旧代码仍会写名称（`NOT NULL` 已经在 `0028` 生效），因此不会绕过索引；只有在需要同时允许重名的旧合同下才要显式 `DROP INDEX accounts_name_key`，那是回退合同、不是回退代码。回退 Web 时保留新增列及已写名称，不执行 `DROP COLUMN`；已有余额、邮箱绑定、标签、密钥和流水在迁移与回退后均保留。

服务端为每个新账户都产生名称（给出的或生成的），因此“账户名称”在接口响应里恒为非空；如果以后要改成允许留空，属于单独修改合同与兼容承诺。

| Spec 判据 | 最小验证切入点 |
| --- | --- |
| V1、V3 | application 生成函数与名称规则单元用例（含邮箱／无邮箱、边界长度、内部连续空格、控制字符、空白、显式 `null` 与省略的区别）；API 合同验证省略即生成、显式 `null` 与空白为 400、原子创建；Playwright 验证表单留空也能提交并显示生成名称、取消不创建、提交中重复点击只发一个请求、响应丢失时先查找确认的提示。 |
| V2 | 真库管理 API 查询用例验证子串、`StarStudio` 这样的大小写不敏感、字面 `%`／`_`、命中多个不同名账户时都列出（靠 id 区分）、名称与邮箱／标签的 AND 组合；Playwright 验证按名称子串查找、筛选不进地址且返回列表时恢复。 |
| V4、V5 | 真库 HTTP 合同验证新建／绑定、生成名称与邮箱本地部分一致、资金与资料保留、唯一冲突及并发回滚；Playwright 验证模式切换、预览迟到响应和提交守卫。 |
| V6 | 真库验证客户会话改名与管理员改名的权限边界、审计操作者与旧新值、改名后账户摘要／账户列表／管理端客户视图／客户会话面四条读都显示当前值（两个方向：客户改运营看得见、运营改客户看得见）；Playwright 验证客户在账户设置改名后刷新显示新值、不能清空，以及运营台改名后列表与详情都读新值。 |
| V7、V8 | 真库验证自注册即得生成名称、客户会话只能改自己账户的名称、未认证改名被拒；`cases_migrations` 在**旧 schema 建行再补迁移**的库上断言 0028 的回填让该行拿到非空名称；沿用并更新详情导航与一次性明文浏览器用例。 |
| V9 | Playwright 验证管理端称谓与提示（“客户登录／开通邮箱登录”、创建表单说明、名称输入框的留空提示）与客户设置页名称说明文案；文案里不出现解释生成规则或内部机制的字样。 |
| V10 | 真库验证：显式名称撞名时创建与改名都返回 `409`（错误码 `name_taken`，与邮箱冲突的 `conflict` 分开）且无写入、仅大小写不同同样冲突、改回自己原名不算冲突、生成路径在首选撞名时换更长片段并成功（同本地部分邮箱的两个账户各得唯一名称）；`cases_migrations` 在“先有重名行再补 0029”的库上验证去重（含改名结果又撞上别的行的构造性撞名）与索引落地；Playwright 验证运营建账户撞名时留在表单、账户详情改名撞名时保留原值、客户在账户设置改成别人的名称被拒并保留原值。 |

实现阶段先更新拥有新行为的浏览器用例，再实现表单与数据流；接口状态与事务验证放在 HTTP 合同测试，不写界面渲染单测。最后按 Web 规则让同一条选定 Playwright 命令连续两次通过；Rust 按改动面跑最小检查，全量交给 CI。规划阶段不运行这些实现测试，也不把计划当作通过证据。
