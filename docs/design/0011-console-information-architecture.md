# 管理后台与客户控制台的信息架构改造方案

- **用途**：修正当前界面的**信息架构**问题。根因是**受众划分错了**：界面按技术领域对象（`Runtime Revision`、`Offering`、`Channel`）分页，而不是按"运营要做的活儿"分页。本方案给出根因、目标结构、每页改造要点、要动后端的部分与不动的部分。
- **读者**：决定做到哪一步的人（产品/运营/技术），以及实施者。
- **合同边界**：管理端导航与账户页组织承接 Spec [`0001-admin-and-customer-consoles.md`](../specs/0001-admin-and-customer-consoles.md)；客户控制台的独立页面与历史浏览由[客户控制台设计](0014-customer-console-navigation-and-history.md)承接，金额展示由[账户资金 Spec](../specs/0002-account-funds-and-reservations.md) §4 定义。

## 1. 根因：界面按技术领域对象分页，而运营与技术开发者要的不是同一件事

`CONTEXT.md` 把这几个概念都定义为**平台内部**的东西：

| 术语 | 定义 | 面向谁 |
| --- | --- | --- |
| Vendor Model Contract | "调用方针对某个 Vendor Model 提交参数时所遵循的合同……表达**模型语义**" | 调用方（技术） |
| Offering | "Provider 通过特定 Adapter 和 Channel 提供某个 Vendor Model Revision 的可调用供给"（词汇表注明「避免叫：模型、渠道」） | 平台内部 |
| Channel | "Provider 的一个调用入口及**凭证身份**，包含地址、凭证引用和启用状态" | 平台内部 |
| Runtime Revision | "一次经过校验并发布的不可变运行时目录" | 平台内部 |

界面把这些内部概念直接做成了运营的导航项，于是出现"发布修订"这一页——**运营看不出它和"网关模型"的区别，也看不出它是干什么用的**。因为两页展示的是**同一个业务对象的技术两面**：

| | 网关模型页 | 发布修订页 |
| --- | --- | --- |
| 渠道 / 渠道模型 | 列出来 | 要填 |
| 驱动器 | 列出来 | 要填 |
| 成本（原币种） | 列出来 | 要填 |
| 对客费率（CNY/1M） | 列出来 | 要填 |

四项重合，其中"驱动器"是纯技术字段。**"一个型号的供给与定价"本来是一个业务对象**，被按"只读视图"与"发布命令"两个技术入口切成了两页。

### 1.1 两类受众的分工

| | 技术开发者关心 | 运营关心 |
| --- | --- | --- |
| 型号 | 合同 schema、原生修订号 | 这个型号**卖不卖、卖多少钱** |
| 供给 | 驱动器名、承载面、参数映射 | **哪家便宜、哪家还能用** |
| 渠道 | `base_url`、凭证变量名 | 这个上游账号**我们还能不能用、哪天挂过** |
| 计价形态 | `token_rates` / `per_image` 的区别 | 不关心，只关心**对客的价目** |

现在界面上没有一处回答运营右列的问题。

**平台只展示输入，不替运营算钱。** 成本与售价**不可直接相减**：成本是"每百万 token 的渠道币种"，售价是"每百万 token 的 CNY"，而利率还分文入／图入／文出／图出四档。谁更便宜、赚多少，是把这些输入连同用量放在一起才成立的判断——那是结算与选路的事（`ADR-0017` 把定价与选路的规则收在各自的读函数上），**不是界面该自己算的一个减法**。所以界面上并列成本与售价、标注币种与口径，不做"毛利"这类合成数。

### 1.2 由此暴露的能力缺口

**渠道没有运营入口**：渠道是**发布时派生**的（按 `provider_kind` + `base_url` + `credential_env` 去重复用），运营手上没有"渠道"这个可管理的对象；唯一可改的是 `PATCH /api/v1/channels/{channel_id}` 的启用开关，而**这个开关在界面上没有入口**。渠道地址与凭证变量名只能从发布表单里进。

**渠道上的钱不在平台的记账范围内**：上游账户还有多少余额，是运营与上游之间的事，平台既不掌握也不该记——平台记的是每个客户欠我们多少（`ledger`）。所以渠道页不出现任何余额字段（§4.2）。

### 1.3 目标结构的原则

1. **按运营的活儿分页**，不按技术对象；
2. **技术入口与运营入口分开**：`POST /api/v1/runtime-revisions` 这个后台接口保留（CI 与部署脚本要用），但它不是运营页面；
3. **运营看得见的是价与状态**：对客价目、成本口径与币种、在售与停用。

## 2. 问题（对截图逐条说）

### 2.1 发布修订：运营看不出它和"网关模型"的区别

这一页最初的全部内容是一段说明 + 一个空 textarea：运营要加一个型号，必须自己拼出 `vendor_id`、`native_model_id`、`native_revision`、`capability_schema`、`offerings[]`（每条候选的渠道、模型名、驱动器、成本单价、币种、计价形态、四档 CNY 费率向量、保底表）以及 `markup_bps`。改成表单之后输入项清楚了，但**它为什么是独立一页、和"网关模型"差在哪，仍然看不出来**——这是 §1 那个根因的直接后果：两页是同一个业务对象的读写两面，重合了渠道、驱动器、成本、对客费率四项字段。

- 手写 JSON 的理由当初是"拆成输入框会让人以为平台在替它做决定"。**这条理由不成立**：Spec M2 说的是"平台只原样保存与冻结、不在服务端替算"，指平台不要算价；运营填 `markup_bps` 与费率，平台依然一个字没算。把"不替算"读成"不给表单"，是设计上的错误推论。
- 改成表单也**没有解决运营的问题**：表单里仍然要填驱动器、承载面、参数映射这些技术字段，而运营要的"这个型号赚多少"两页都没有。

### 2.2 账户与密钥：六个独立操作堆成一页长滚动

截图 `05-运营后台-账户与密钥.png` 从上到下是：查一个账户 → 建账户/充值/标签（三列并排）→ API Key → 客户登录身份。

| 问题 | 具体表现 |
| --- | --- |
| **顺序错** | "查账户"是这一步的先决条件（下面每个操作都要账户标识），却只在页首一行；运营读完余额要滚回下面充值，改完再滚上去核 |
| **权重错** | 充值是最频繁的操作，与"标签"（一次性配置）等权并排；页面没有"最常做什么"的答案 |
| **分组错** | 客户登录身份（开户、按邮箱找、签重置令牌）是**客户管理**，与"账户与密钥"是两件事，塞在一起后谁都不完整 |
| **入口错** | 查账户只有"账户 id（UUID）"一个输入框。运营手上没有 UUID，他们有的是邮箱或标签——Spec M5 明确要求"按邮箱找到客户账户"，而它被埋在下面那一小块里 |
| **无列表** | "有哪些账户""谁的余额快没了"在这一页看不到；运营必须先知道 id 才能做事 |

### 2.3 客户控制台：四块全在一页

截图 `11-客户控制台-控制台.png` 竖排四块：余额与持有 → 改口令 → API Key → 用量与账单。

- 客户**唯一常看**的是余额与用量；改口令是一次性动作，却占了中间一层，把两件常看的事隔开。
- 没有导航：用量条数多起来之后无法定位，也无法"只看用量"。
- 账务三块（余额、流水、用量与账单）本是一件事的三个视角，现在被"改口令"切开。

## 3. 目标结构

组织原则是**按运营的活儿分页**（§1.3），而不是按技术对象或端点：

| 层 | 承担什么 | 形态 |
| --- | --- | --- |
| **导航** | 运营的工作区（见 §3.1）；技术入口单独收在一处，不混进运营导航 | 侧栏 |
| **列表页** | "有哪些东西、各自什么状态" | 可搜索、可排序、可分页的表格 |
| **详情页** | "这一个东西的全部细节与可做的动作" | 抽屉或独立视图，动作按频次排序 |
| **危险动作** | 停用、退款、吊销 | 二次确认 + 结果反馈 |

### 3.1 管理端的导航

| 工作区 | 里面是什么 | 运营在这里回答的问题 |
| --- | --- | --- |
| **模型目录** | 在售型号的列表：对客名、状态（在售/停售）、对客价目、成本与它的币种；点开看候选渠道与各自成本、启停（改价的完整形态取决于 §4.1 的选型） | **我们卖什么、卖多少钱、哪家便宜** |
| **渠道** | 上游账号列表：类别、地址、凭证变量名、启用状态、被哪些型号用着；停用/启用 | **上游哪家还能用、哪家挂了** |
| **账户** | 按邮箱／标签找账户的列表页 → 该账户的独立详情页（金额、标签、充值、记录、API Key 签发） | **谁还欠费、给谁充值** |
| **客户登录** | 开通邮箱登录与按邮箱找登录身份的列表页 → 该身份的独立详情页（身份、关联账户、重置令牌） | **这个客户的账号是什么** |
| **诊断** | 对账案例、平台侧失败、成本缺口 | **哪笔钱要人工去核** |
| **设置** | 折算率、路由策略 | 低频配置 |

**关键改动：原来的"网关模型"与"发布修订"合成「模型目录」一页。** 它们是同一个业务对象（一个型号的供给与定价）的读与写；分成两页之后重合四项字段，"驱动器""承载面"这类技术字段出现在运营面前，而对客价目与成本口径这两组数分在两页、没法对着看。

**"发布修订"命令降级成技术入口**：`POST /api/v1/runtime-revisions` 保留（CI 与部署脚本要用），界面上收在「模型目录」的一个折起入口里，写明"面向技术：新增型号或重签合同；只改价格请用型号详情里的表单"。新增型号时必须贴厂商合同（JSON Schema），那是技术活。

### 3.2 客户控制台的形态

客户控制台的五个独立页面、固定导航与历史浏览见[客户控制台设计](0014-customer-console-navigation-and-history.md) §1–§3；管理端各页由下文规定。

## 4. 逐页改造要点

### 4.1 模型目录（M1 + M2）

一页承担两件事，因为它们是同一个业务对象：

**读（取代现在的"网关模型"页）**：型号列表给出运营要看的数——对客名、状态、**各档对客价目**、成本与它的币种。现在这一页列的是档位、权重、驱动器、承载面、成本口径：除了成本，其余都是技术字段，而对客价目在另一页。

**写（取代现在的"发布修订"页）**：分两个入口，按谁来做分开：

| 入口 | 谁做 | 形态 |
| --- | --- | --- |
| **改价 / 上下架** | 运营 | 型号详情里改倍率或售价 → 保存；停售一个候选就是一个开关 |
| **新增型号 / 重签合同** | 技术 | 折起的"高级"入口：贴厂商合同（JSON Schema，只能贴）+ 配候选的技术字段 |

**改价目前不能用表单直接完成的原因与已定的解法**：`PublishRuntimeCommand` 要求 `offerings` 是**完整、有序**的集合（必填、非空），每次发布都要给全；而候选的渠道三要素（`provider_kind`、`base_url`、`credential_env`）与驱动器是渠道部署事实，管理端的模型视图不回显它们。所以前端拼不出完整命令，只能把这些字段摆给运营。

**已定：发布命令支持增量**——渠道三要素与驱动器可整组省略，服务端从该型号当前生效的修订按 `provider_kind` + `provider_model_id` 取同一条候选的值补上，歧义或沿用不到即拒。合同见 [`0010-identity-and-consoles.md`](0010-identity-and-consoles.md) §4.1。落地之后：运营改价 = 选型号 → 改倍率或对客费率 → 保存，表单里不出现渠道技术字段；「网关模型」与「发布修订」也就可以合成一页。

### 4.2 渠道

上游账号的列表：类别、地址、凭证变量名、启用状态、被哪些型号用着。动作只有停用/启用（`PATCH /api/v1/channels/{channel_id}` 已有，界面没入口）。

**渠道上的钱不归平台管。** 上游账户还有多少余额，是运营与上游之间的事，平台既不知道也不该记——记账在渠道那边，平台记的是**每个客户欠我们多少**（`ledger`）。所以渠道页只回答"我们能用哪些上游账号、哪个被停用了"，不出现任何余额字段。

### 4.3 账户（M5 的前半）

- **列表与导航**：`#/accounts` 只显示名称／邮箱／标签筛选、账户列表、按完整账户 id 查看与建账户入口。列表列出**账户名称**、账户 id、邮箱、标签、已结算余额和创建时刻；名称是主要识别文字（规则见[账户名称 Spec](../specs/0003-account-names-and-login-identities.md)）。点行或按 id 查看后进入 `#/accounts/{account_id}`；建账户成功也进入新账户详情。详情在主内容区替换列表，不把摘要接在列表下面。侧栏“账户”在两个地址都保持选中；详情有返回列表入口，浏览器后退也返回原列表及本次筛选。
- **详情首屏**：按地址中的 id 分别读取 `GET /api/v1/accounts/{account_id}/summary`（账户名称、账户 id、标签、绑定邮箱）和既有 `GET /api/v1/accounts/{account_id}`（已结算余额、持有中、可用额）；详情不依赖列表曾经加载的行数据，因此直接打开和刷新都能取到当前账户。名称与标签各自保存后重取摘要，两者分开提交。金额直接用余额读接口字段，不在页面重算，也不展示单笔预授权额或释放额。账户金额含义由[账户资金 Spec](../specs/0002-account-funds-and-reservations.md) §4 负责。任一读表明账户不存在时显示找不到，不用上一个账户的读数或标签填充。
- **详情内的四项操作**：在金额和标签下用页内导航切换“充值”“充值记录”“扣费记录（调用明细）”“API Key”，一次只挂载当前模块，不再从列表页下方的“选中账户”区打开弹窗或侧边栏。切换模块不改变账户主体；切换账户或离开详情时销毁旧模块状态和一次性明文。只在打开对应模块时读取其数据。
- **充值与记录**：充值模块只填金额；一次充值意图的幂等键由页面生成，提交失败后沿用同一个键，成功后换键并刷新余额与充值记录。充值记录只列实际 `credit` 的时刻与金额；扣费记录逐笔列请求时刻、型号、状态、按模型类型的用量、实际扣费与请求任务 ID，未收费显示零。预授权与释放不进入这两类记录。账户资金流水科目由[账户资金 Spec](../specs/0002-account-funds-and-reservations.md) §3 定义。
- **API Key**：详情的 API Key 模块**只签发、不吊销**——运营判断不了客户是否正在正常使用，也拿不到要吊销的密钥标识（它只出现在签发响应里），吊销是客户自己的事（Spec `0001` M5、C5）。签发的明文放在**弹窗**里（内容只有密钥本身，不显示密钥标识），关闭弹窗、切换账户或刷新即从页面状态清除；模块本身不再摆任何吊销表单。
- **建账户**：列表页右上角打开表单，填写**可选账户名称**、可选标签和初始充值；三者**一次提交**（不再有"账户建好了但标签没写上"的中间状态），取消不建账户。名称留空即由服务端生成，输入框里写明这一点；提交过程禁止重复点击，响应丢失时提示先按名称查找确认。

### 4.4 客户（M5 的后半 + C12/C13）

- **列表与导航**：`#/customers` 只显示“开通邮箱登录”、按邮箱查找及登录身份列表；列表包含**关联账户名称**、邮箱、绑定账户、创建时间、上次登录。点“详情”进入 `#/customers/{customer_id}`，开通成功也进入新客户详情。详情替换查找列表；侧栏“客户登录”保持选中。返回列表和浏览器后退保留本次查找条件。
- **详情读取**：用新的管理员 `GET /api/v1/customers/{customer_id}` 按地址中的 id 取客户视图，显示**关联账户名称**、邮箱、账户、创建时间、上次登录（名称取自关联账户的当前值，不另存副本）。该读不依赖刚才的列表或开户响应，因此直接打开与刷新可用；不存在时显示找不到，不留下先前客户资料。关联账户 id 是通往 `#/accounts/{account_id}` 的入口，运营无须复制标识再查一次。
- **开户与重置**：页面标题、导航与入口用“客户登录”“开通邮箱登录”；表单显式给两个模式——**新建账户并开通邮箱登录**（必填登录邮箱、可选账户名称与初始口令，名称留空即按邮箱生成）与**为已有账户开通邮箱登录**（必填已有账户 id，先预览确认对象：显示名称、完整 id 与登录状态；只有当前输入 id 的成功预览能用于确认，预览说它已绑定时不能提交），绑定不覆盖已有名称。客户详情里签发重置令牌，明文只在本次签发后的可关闭提示中显示，关闭、离开详情或刷新即清除，并写明一次有效、30 分钟过期、由运营当场转交。列表页不承载令牌明文。

### 4.4.1 管理端详情地址

管理端沿用现有 `#` 路由，不改静态托管；路由解析增加账户与客户的 id 段，并把同一工作区的列表与详情映射到同一个侧栏项。详情页按 id 独立取数；无管理员会话时登录页阻止详情挂载与管理请求，登录后保留目标地址。未知页面和不存在的 id 显示管理端找不到状态。地址只含不透明 id，不含会话凭据、API Key、重置令牌或搜索邮箱。两张列表的最近一次筛选放在当前浏览器会话的页面状态中，详情刷新、返回列表或前进后退时恢复；退出或会话失效时清除，不把邮箱写入 URL。

### 4.5 客户控制台

页面组织、筛选、翻页与密钥操作由[客户控制台设计](0014-customer-console-navigation-and-history.md)承接；金额与预授权展示由[账户资金 Spec](../specs/0002-account-funds-and-reservations.md) §4 承接。

## 5. 哪些不做

- 本文负责的管理端页面组织不改已有管理端点的**状态码与鉴权**，也不改既有取值的含义；为详情直达新增的只读端点见 §6.3。客户账务读的扩展由[客户控制台设计](0014-customer-console-navigation-and-history.md) §2–§3 负责；
- 不给管理端加"替客户支付/充值到对客通道"之类的入口（Spec §3 非目标）；
- **不在平台上记渠道上游的钱**：余额、欠费、已充值额都不进这个系统。平台记的是每个客户欠我们多少（`ledger`）；上游账户的钱在渠道那边，运营自己与上游结算；
- **不做一个"毛利"这类合成数**：成本与售价币种不同、费率还分四档，谁更便宜是把输入连同用量放在一起才成立的判断，归结算与选路（§1.1）；
- 不做主题化、暗色模式、多语言——与本方案要解决的问题无关；
- 管理端不在这一轮做移动端适配；客户控制台的窄屏导航由[客户控制台设计](0014-customer-console-navigation-and-history.md) §1 承接。

## 6. 要动后端的部分

### 6.1 已经具备的（本次改动落地）

| 需要的能力 | 原来的状况 | 做法 |
| --- | --- | --- |
| 账户列表 / 按标签或邮箱搜索账户 | 只有 `GET /api/v1/accounts/{id}` | 新增 `GET /api/v1/accounts?tag=&email=&limit=`（只读；按创建时间倒序）。列表项**带绑定的登录邮箱**（没有登录身份时为 `null`）：运营按邮箱找账户，搜出来的行必须能确认是谁 |
| 账户分页流水 | `GET /api/v1/accounts/{id}/entries` 只有 `since` + `limit`，无上界、无总数 | 增加可选的 `until` 与 `offset`，响应增加 `total`；`truncated` 的含义落成"这个位置之后还有没有更多"（`offset + count < total`），区间为半开 `[since, until)` |

### 6.2 按 §4.1／§4.2 还需要新增的（待定）

| 需要的能力 | 为什么 | 依赖的选型 |
| --- | --- | --- |
| 服务端支持增量发布 | "改价"是最常见的运营动作，今天要重拼整份发布命令，于是技术字段全摆到运营面前 | §4.1 已定：走增量发布 |
| 渠道列表与启停入口 | 运营看不到"我们有哪些上游账号、哪家挂了" | 只需把既有的 `PATCH /api/v1/channels/{channel_id}` 与一条读列表接上界面（§4.2） |

发布页的算价算式只做**展示层算术**（初始对客价 = 该 vendor/模型已知渠道价目 × 倍率 × 折算率，运营可改），不新增端点。

### 6.3 管理员账户与客户详情的按 id 读取

管理员详情直达需两条只读端点：`GET /api/v1/accounts/{account_id}/summary` 按 id 返回既有 `AccountSummary`，`GET /api/v1/customers/{customer_id}` 按 id 返回既有 `CustomerView`。现有账户列表只按邮箱或标签筛选且最多返回受限数量，不能在刷新一个较旧账户的详情时当作按 id 读取；现有客户列表只按邮箱筛选或取最近若干个，不能在刷新客户详情时稳定恢复。两个新端点走现有管理认证与响应错误约定，不改已有列表或余额接口；不存在的 id 返回 404。数据从现有账户与身份表读取，不新增持久表，不返回凭据。

## 7. 验收判据

见 Spec 的 V-D 系列（[`0001-admin-and-customer-consoles.md`](../specs/0001-admin-and-customer-consoles.md) §5.3）。其中 V-D15 用浏览器验证两处列表进入独立详情、直接打开与刷新、前进后退、未登录回跳、对象不存在时清屏；两条按 id 读取的管理端点用接口合同用例验证认证、存在、不存在和响应字段。页面布局是否仍把列表与详情纵向拼接，需人工打开桌面页面核对。

V-D9（改价不用重新填技术字段）依赖 §4.1 已定的增量发布。若按本方案的受众划分，还应当补一条：**运营改价不需要进入任何技术入口**。

## 8. 落地顺序

1. **服务端支持增量发布**（§4.1 已定）：发布命令允许省略候选的技术字段，从该型号当前生效的修订取；
2. 改价 / 上下架的表单（依赖 1）：运营在型号详情里改一个数就能发新修订；
3. 模型目录：把"网关模型"与"发布修订"合成一页，把对客价目与成本口径并列摆出来；
4. 渠道页（依赖 §6.2 的渠道列表读）。
