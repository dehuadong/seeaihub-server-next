# 管理后台与客户控制台的信息架构改造方案

- **用途**：修正当前界面的**信息架构**问题——它不是样式问题，而是"按端点分组摆控件"而不是"按运营的工作顺序组织"。本方案给出目标结构、每页的改造要点、要动后端的部分与不动的部分。
- **读者**：决定做到哪一步的人（产品/运营/技术），以及实施者。
- **合同边界**：Spec [`0001-admin-and-customer-consoles.md`](../specs/0001-admin-and-customer-consoles.md) 的 M1–M7、C1–C14 与验收条件 V-* 不变；本方案只改**界面怎么组织**，不改任何端点的行为与验收口径。哪些端点的响应形状可以扩展，见第 5 节。
- **状态**：待评审。评审通过后才进入实施。

## 1. 问题（对截图逐条说）

### 1.1 发布修订：唯一的加型号入口要求手写 JSON

截图 `02-运营后台-发布修订.png` 的全部内容是一段说明 + 一个空 textarea。运营要加一个网关模型，必须自己拼出 `vendor_id`、`native_model_id`、`native_revision`、`capability_schema`、`offerings[]`（每条候选的渠道、模型名、驱动器、成本单价、币种、按张/按次/token 三种形态的选择、四档 CNY 费率向量、保底表）以及 `markup_bps`。

- 这是**高频且不可替代**的操作（没有别的路径能让一个型号出现在对客目录里），却要求手写结构化 JSON。
- 原先的理由是"拆成输入框会让人以为平台在替它做决定"。**这条理由不成立**：Spec M2 说的是"平台只原样保存与冻结、不在服务端替算"，指平台不要算价；运营在表单里填 `markup_bps` 与四档费率，平台依然一个字没算。把"不替算"读成"不给表单"，是设计上的错误推论。
- 后果：运营出错只能靠发布期的报错逐条猜；改一次价要重贴整份 JSON。

### 1.2 账户与密钥：六个独立操作堆成一页长滚动

截图 `05-运营后台-账户与密钥.png` 从上到下是：查一个账户 → 建账户/充值/标签（三列并排）→ API Key → 客户登录身份。

| 问题 | 具体表现 |
| --- | --- |
| **顺序错** | "查账户"是这一步的先决条件（下面每个操作都要账户标识），却只在页首一行；运营读完余额要滚回下面充值，改完再滚上去核 |
| **权重错** | 充值是最频繁的操作，与"标签"（一次性配置）等权并排；页面没有"最常做什么"的答案 |
| **分组错** | 客户登录身份（开户、按邮箱找、签重置令牌）是**客户管理**，与"账户与密钥"是两件事，塞在一起后谁都不完整 |
| **入口错** | 查账户只有"账户 id（UUID）"一个输入框。运营手上没有 UUID，他们有的是邮箱或标签——Spec M5 明确要求"按邮箱找到客户账户"，而它被埋在下面那一小块里 |
| **无列表** | "有哪些账户""谁的余额快没了"在这一页看不到；运营必须先知道 id 才能做事 |

### 1.3 客户控制台：四块全在一页

截图 `11-客户控制台-控制台.png` 竖排四块：余额与持有 → 改口令 → API Key → 用量与账单。

- 客户**唯一常看**的是余额与用量；改口令是一次性动作，却占了中间一层，把两件常看的事隔开。
- 没有导航：用量条数多起来之后无法定位，也无法"只看用量"。
- 账务三块（余额、流水、用量与账单）本是一件事的三个视角，现在被"改口令"切开。

## 2. 目标结构

组织原则换成**按使用频次与工作顺序**，而不是按端点：

| 层 | 承担什么 | 形态 |
| --- | --- | --- |
| **导航** | 五个工作区：模型与发布、账户、客户、诊断、折算率与路由（见下） | 侧栏 |
| **列表页** | "有哪些东西、各自什么状态" | 可搜索、可排序、可分页的表格 |
| **详情页** | "这一个东西的全部细节与可做的动作" | 抽屉或独立视图，动作按频次排序 |
| **危险动作** | 停用、退款、吊销 | 二次确认 + 结果反馈 |

### 2.1 管理端的五区导航

| 工作区 | 包含 | 与现在的差别 |
| --- | --- | --- |
| **模型** | 网关模型列表 → 详情抽屉（候选、成本、费率、启停），**发布修订从这一区发起**（"加一个型号"与"给已有型号发新修订"是同一个动作的两个入口） | 现在把候选展开在页面里，型号一多就成一片表格；而且"发布"与"看结果"分在两个区，发完要跳过去核对 |
| **账户** | 账户**列表**（搜索：邮箱 / 标签 / 账户 id）→ 详情抽屉（余额、流水、充值、标签、密钥） | 从"先有 id 才能查"改成"先搜到，再操作"；充值进详情、按频次排在第一位 |
| **客户** | 客户列表（邮箱、绑定账户、上次登录）→ 详情（改初始口令、签重置令牌、绑到已有账户） | 从"账户页里的一小块"独立成区；Spec M5 的"按邮箱找客户账户"成为主入口 |
| **诊断** | 对账案例、平台侧失败、成本缺口 | 基本不动（三张清单已经按"要做什么"分好了） |
| **设置** | 折算率、路由策略 | 两者都是低频配置，合并为一区，不占主位 |

### 2.2 客户控制台的形态

| 现在 | 目标 |
| --- | --- |
| 一页竖排四块 | **顶部一条概览**（可用余额、持有中、本月扣费）+ 三个标签页：`用量与账单`、`API Key`、`账户设置` |
| 改口令夹在余额与密钥之间 | 进"账户设置"标签页（低频动作不占主视线） |
| 金额与用量混在长页里 | 概览给三个数，明细在各自标签页内分页 |

## 3. 逐页改造要点

### 3.1 发布修订（M2）

保留"贴 JSON"作为**兜底**，但把主路径改成向导：

1. **选来源**：厂商 + 原生型号名 + 合同修订号。可从已发布型号"另存为新的修订"（改价最常见的场景）。
2. **贴合同**：`capability_schema` 仍是结构化对象，给一个带 schema 校验的编辑器（不是裸 textarea）+ "用上一次的合同"。
3. **配候选**：一条候选一张卡片——渠道、渠道模型名、驱动器、档位与权重、**计价形态单选**（按张 / 按次 / 按 token / 上游给金额）、成本单价与币种。
4. **算价预览**：按选中的形态显示"对客价 = 成本单价 × 倍率 × 折算率"的**只读算式与结果**，费率向量的四档可直接填、也可由这个算式**预填后由人确认**（记一笔说明"这是你的输入，平台只是照着算给你看"，与 M2 的"平台不替算"一致——它是展示，不是决定）。
5. **发布前校验**：本地先跑一次"缺折算率 / 缺倍率 / 形状不对"的检查并列出，减少一轮往返。
6. **发布结果**：修订标识 + 跳转到该型号详情。

### 3.2 账户（M5 的前半）

- **列表**：账户 id（截断可复制）、标签、余额、写入时刻；搜索框支持**邮箱 / 标签 / 完整 id**；余额为负或持有中异常的用颜色标出。
- **详情抽屉**：余额与持有（分列）→ 充值（第一顺位，常用金额快捷键）→ 流水（分页）→ 标签 → 密钥（签发/吊销）。
- **危险动作**：吊销密钥二次确认；发密钥的明文用一次性弹层。
- **保留** "按 id 直接查"作为列表不可用时的兜底（例如刚建的账户）。

### 3.3 客户（M5 的后半 + C12/C13）

- **列表**：邮箱、绑定账户、创建时间、上次登录；搜索按邮箱（Spec M5 的要求）。
- **开户**：表单（邮箱 + 初始口令可选 + "绑到已有账户"可搜索选择），而不是先抄一个账户 id 再回来填。
- **签重置令牌**：在客户详情里一键签发，令牌明文用一次性弹层 + 复制，并写明"只用一次、30 分钟过期、当场转交"。

### 3.4 客户控制台

- 顶部概览：**可用余额 / 持有中 / 区间扣费**三个 `Statistic`；
- 标签页：`用量与账单`（默认，含汇总与明细）、`API Key`、`账户设置`（改口令 + 退出 + 账号信息）；
- 用量与流水各自分页（服务端已支持 `limit` 与 `since`/`until`，前端目前只拉 50 条不分页）。

## 4. 哪些不做

- 不改任何端点的**行为、状态码、鉴权与验收口径**；
- 不给管理端加"替客户支付/充值到对客通道"之类的入口（Spec §3 非目标）；
- 不做主题化、暗色模式、多语言——与本方案要解决的问题无关；
- 不在这一轮做移动端适配（运营在桌面用；客户端当前布局已经可窄屏）。

## 5. 要动后端的部分（需要单独确认）

界面要"先搜到再操作"，而今天的端点只支持"知道 id 才查"。下面两条是**新增读端点**，不改既有端点：

| 需要的能力 | 今天的状况 | 建议 |
| --- | --- | --- |
| 账户列表 / 按标签或邮箱搜索账户 | 只有 `GET /api/v1/accounts/{id}` | 新增 `GET /api/v1/accounts?tag=&email=&limit=`（只读；按创建时间倒序） |
| 账户分页流水 | `GET /api/v1/accounts/{id}/entries` 只有 `since` + `limit`，无 `until`、无总数 | 扩展为 `since`/`until`/`limit`/`offset`，响应带 `count` |

另外，发布向导的"预填费率"只做**展示层算术**（成本单价 × 倍率 × 折算率），不新增端点、不改 M2 的"平台不替算"。

**如果这两条不加**，账户区只能退化成"按 id 或邮箱查单个账户"（邮箱那条走既有的 `GET /api/v1/customers?email=` 再取 `account_id`），列表与搜索做不出来。这一步需要你决定。

## 6. 验收（界面部分的建议判据）

以下判据建议加进 Spec 的 V-D 系列（现有 V-D1…V-D7 不动）：

| 编号 | 判据 |
| --- | --- |
| 新增 | **加一个网关模型不需要手写 JSON**：用向导走完"选来源 → 配候选 → 发布"，能发布成功并在模型列表看到它 |
| 新增 | **充值不需要先知道账户 id**：用邮箱或标签搜到账户 → 在详情里充值 → 余额与流水立刻反映 |
| 新增 | **替客户开户不需要先抄账户 id**：在客户区用邮箱开户（新建或绑已有账户），随后能签发重置令牌 |
| 新增 | 客户控制台**首屏能看到余额与持有**（不需滚动），且改口令不在首屏占用主位 |

## 7. 实施顺序（建议）

1. 账户区与客户区分家 + 客户列表与开户（要 5 节的第一条端点）；
2. 发布向导（不依赖后端改动，收益最大）；
3. 客户控制台改为概览 + 标签页（不依赖后端）；
4. 模型详情抽屉、账户分页流水（依赖 5 节的第二条端点）。
