# 领域工程判断

本文件只定义进行领域判断时读什么、如何使用术语、怎样处理冲突，以及什么架构决定值得单独建档。文档位置与职责见 [`docs/AGENTS.md`](../AGENTS.md#文档分层)。

## 判断前读取

先读取 [`docs/AGENTS.md`](../AGENTS.md#历史归属切换)，从同一入口取得当前产品合同、技术设计与决定属主、历史来源和未完成切换的范围。领域指南不另维护目录优先级或属主表。

再按问题读取根 [`GLOSSARY.md`](../../GLOSSARY.md)、工作项的行为与验收、适用的 Agent Note、`docs/facts/` 的渠道事实，以及代码和测试证据。旧 Spec 仅作历史依据；工作项拥有本次行为与验收，Note 拥有长期技术设计与决定；生命周期不替代评审、批准或实施授权。

未完成承接或接受范围不明的历史内容，依赖它的新工作先解决有效范围和评审缺口。代码只证明实现，不自动批准旧草案；调研与原始材料只作证据。

## 使用词汇表术语

命名领域概念时（Issue 标题、提案、类型、测试名），使用 `GLOSSARY.md` 定义的说法，不使用其中明确要求避免的同义词。

若需要的概念还不在词汇表里，这是一个信号：要么你在发明项目不用的语言（重新考虑），要么存在真实的词汇缺口（记为缺口，交给 `domain-modeling`）。

## 标注冲突

当输出与已交付的决定冲突时，显式指出而不是静默覆盖，并引用具体文档：

> _与 `docs/design/0001-image-generation.md` 的「不自动重提，创建 Reconciliation Case」冲突——但值得重开，因为……_

发现冲突不等于立即改写权威文档；先确认是事实变化、实现偏离还是合同需要重新批准，再更新相应属主。

## 持久决定的准入与引用

长期技术提案、设计与决定使用文档入口登记的 Agent Notes；同一决定更新已有 Note，不再新建 RFC 或 ADR。只有架构决定需要单独建档时，使用 [`adr` 技能](../../.agents/skills/adr/SKILL.md) 的三条准入条件：难以逆转、脱离上下文令人困惑、存在真实权衡。这些条件不限制普通技术设计 Note。

写清改变决定要迁移什么、真实备选、选择理由及接受的代价。没有历史备选记录时明确标注缺口，不编造。新工作的产品行为、安全与兼容合同归工作项；可变取值归发布物或配置参考；实测结论归渠道事实。

被取代的历史文件保留原文、原编号和失效范围，链接现行属主，不降成删除正文的存根。历史 ADR 使用 `ADR-xxxx` 或具体相对链接，未来开发从统一归属入口解析有效范围。其他引用规则见 [`docs/AGENTS.md`](../AGENTS.md)。
